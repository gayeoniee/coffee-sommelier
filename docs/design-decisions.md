### 1. 왜 FastAPI인가

추천 API는 카드를 먼저 보내고 설명 3개를 토큰 단위로 스트리밍(SSE)해야 하며, 설명 LLM 호출 3개를 동시에 돌려야 한다. FastAPI는 네이티브 async, Pydantic 입출력 검증(1단계 데이터 모델이 이미 Pydantic), `StreamingResponse`를 기본으로 갖고 있어 Flask(async가 부가 기능)나 DRF(이 규모엔 무거움)보다 요구에 바로 맞았다. 설명 3개를 병렬로 돌리자 순차 4.59초가 2.03초로 줄었다. 원자료: [ADR 0001](adr/0001-fastapi.md), [phase2_bench.json](../data/eval/phase2_bench.json).

### 2. 왜 LangGraph인가, LangChain은 왜 안 썼나

AI 흐름에는 분기("DB에 있는 원두인가"), 폴백(LLM 실패 → 템플릿, 임베딩 실패 → 산지·가공 평균), 병렬(`Send`로 설명 3개)이 있고 LangGraph는 이 셋을 그래프로 그대로 표현한다. LLM 호출은 1단계에서 만든 자체 클라이언트를 쓰므로 LangChain 의존성은 들이지 않았다. 그래프는 3개(`recommend` 3노드, `analyze_bean` 5노드, `log_tasting` 4노드)이고, 노드는 `app/core/`의 순수 함수를 감싼 얇은 래퍼라 로직은 그래프 없이 테스트된다. 이 구조 덕분에 설명 모델을 TTFT 0.8초짜리 llama에서 nemotron으로 되돌릴 때(llama가 산미 4.5 선호 손님에게 "산미를 좋아하지 않아"라고 정반대 설명을 씀) 그래프는 건드리지 않고 `config/models.yaml`만 바꿨다. 원자료: [ADR 0002](adr/0002-langgraph.md), [graphs.md](graphs.md).

### 3. 왜 별도 벡터 DB 대신 pgvector + HNSW인가

추천의 절반은 SQL 필터(카페인·우유·브랜드)이고 나머지 절반이 벡터 유사도라, 둘을 한 쿼리에서 거는 게 가장 단순하다. 와인 v1은 Pinecone + 프롬프트 속 필터였고 필터가 실제로는 걸리지 않았다. 문제는 필터가 좁을 때였다 — 디카페인은 9,155개 중 168개(1.8%)뿐이라 HNSW가 필터 뒤에 k개를 못 채웠고, `hnsw.iterative_scan = relaxed_order`로 해결했다. 무료 등급 Neon 하나로 사용자 기록·프로필까지 같은 DB에 두고, 이웃 쿼리는 인덱스를 탄 채 1.5ms(EXPLAIN ANALYZE)다. 원자료: [phase2_coverage.json](../data/eval/phase2_coverage.json), [ADR 0006](adr/0006-deterministic-neighbors.md).

### 4. 왜 조건은 필터, 취향은 점수인가

카페인·우유는 어기면 안 되는 조건이라 점수에 섞으면 "취향 점수가 아주 높은 일반 커피"가 디카페인 손님에게 올라올 수 있다. 그래서 `passes`(하드 필터)를 먼저 통과시키고, 산미·바디·향미는 `score_item`(속성 0.6 + 향미 0.4)로 순위만 매긴다. 평가는 추천 코드와 독립인 라벨(메뉴 이름 453종 수기 우유 라벨, 원본 메뉴의 디카페인 필드)로 하는데, 필터를 고치기 전 판정 로직은 3/78건(마키아또·콘 파나·플랫 화이트를 우유 불가 손님에게)을 어겼고 지금은 페르소나 4 × 브랜드 10에서 0/108건이다(이디야 메뉴 추가 전 0/102). 원자료: [phase2_violations.json](../data/eval/phase2_violations.json).

### 5. 왜 규칙을 먼저 쓰고 빈 칸만 LLM에 맡기나

원두 약 9천 건을 전부 LLM에 돌리면 시간이 배로 들고, 원본 점수·키워드로 확실히 채울 수 있는 칸까지 모델의 흔들림에 맡기게 된다. 규칙으로 못 채운 5,035건만 로컬 `qwen3.5:9b`로 처리했고 실패는 0건, 비용은 0원이었다. 실버 정답(다른 벤더 판정자) 대비 LLM이 채운 산미는 ±1 이내 95.65%(n=23)로, 원본 점수를 5분위로 바꾼 값(62.5%, n=16)보다 오히려 정확했다. 판정자 두 명끼리의 산미 ±1 일치는 100%라 이 실버 라벨을 기준으로 쓸 만하다. 원자료: [gold_enrich_judge2_scores.json](../data/eval/gold_enrich_judge2_scores.json), [gold_agreement.json](../data/eval/gold_agreement.json).

### 6. 왜 이웃 예측에 신뢰도와 근거를 붙이나

처음 보는 원두는 유사 원두 10개의 가중 평균으로 산미·바디를 추정하는데, 이웃이 서로 엇갈리면 평균은 그럴듯해 보여도 틀리기 쉽다. 그래서 이웃 분산으로 신뢰도(낮음/보통/높음)를 매기고 근거 원두를 함께 보여준다. leave-one-out에서 신뢰도는 실제 정확도와 순서가 맞았다 — 산미 ±1 이내가 낮음 0.1818(n=11), 보통 0.7317(n=123), 높음 0.8333(n=66)로, 전체 0.735(n=200)를 사용자가 "얼마나 믿을지"로 쪼개 준다(대상 200개 자체는 바디 재라벨 전과 같지만, 신뢰도는 이웃의 산미·바디·단맛 분산으로 매기므로 이웃의 바디 값이 재라벨되면서 각 대상이 속하는 신뢰도 구간도 소폭 바뀌었다 — [ADR 0010](adr/0010-body-heaviness.md)). 임베딩 API가 실패하면 산지·가공 평균으로 떨어지고 신뢰도는 강제로 "낮음"이 된다. 원자료: [phase2_loo.json](../data/eval/phase2_loo.json).

### 7. 왜 템플릿 폴백과 12초 마감을 두나

설명 LLM은 무료 NVIDIA 엔드포인트라 가끔 수십 초씩 멈추고, 설명이 안 와도 추천 자체는 유효하다. 그래서 카드는 템플릿 설명과 함께 먼저 보내고(`cards` 이벤트), LLM 설명이 실패하거나 12초 마감을 넘기면 `explain_fallback`으로 템플릿을 확정한다. 운영에서 thinking을 끄기 전 폴백은 3/8(37%), 끈 뒤 6개 브랜드 카드 18장에서 2/18(11%)였고, 설명 품질 평가 2차에서는 0/24였다. 남은 폴백은 NVIDIA 쪽 꼬리 지연이라, 첫 토큰이 3초(평소 p95 1.37초의 두 배 이상) 안에 안 오면 같은 요청을 하나 더 보내 먼저 오는 쪽을 쓰는 헤지 요청을 더했다(ADR 0004 "헤지 요청" 절; 카드당 추가 요청은 최대 1개). 템플릿도 평가 대상이라 1차 평가에서 "+200원 환각"(추가요금이 페이로드에 없었음)을 잡아 고쳤다. 그런데 운영 48시간 로그를 쪼개 보니 남은 폴백(카드 5/56)은 꼬리 지연이 아니었다 — 5건 모두 첫 토큰 없이 요청 전체가 1.1~1.7초에 끝난 **빠른 실패**(NVIDIA 429·빈 200 응답)였고, 헤지 타이머가 돌기 전에 끝나 곧장 운영에 없는 로컬 폴백으로 넘어가 템플릿이 됐다. 그래서 첫 요청이 출력 없이 끝나면 1초 뒤 같은 요청을 한 번 더 보내는 조기 실패 재시도를 더했다(헤지와 추가 요청 1개 예산 공유). 운영 조건 재현 A/B에서 폴백 10/140 → 0/140. 원자료: [ADR 0004](adr/0004-explain-thinking.md), [ADR 0005](adr/0005-explain-quality-eval.md), [phase2_fallback_retry.json](../data/eval/phase2_fallback_retry.json).

### 8. 왜 설명 모델의 thinking을 껐나

`nemotron-3-super-120b`는 기본으로 생각(chain-of-thought)을 한 뒤 답해서 첫 토큰까지 10.6초가 걸렸고, `<think>` 내용이 스트리밍 텍스트에 섞여 나왔다. `chat_template_kwargs: {enable_thinking: false}` 한 줄로 첫 토큰이 0.67초가 됐다. 대가를 재기 위해 파싱 태스크의 자기일관성을 on/off로 비교했고 96.29% → 94.21%(−2.08%p)로, 미리 정한 허용 기준(−5%p) 안이었다. 코드 변경 없이 설정만 바꿨으므로 한 줄을 지우면 되돌아간다. 원자료: [ADR 0004](adr/0004-explain-thinking.md), [phase2_thinking.json](../data/eval/phase2_thinking.json).

### 9. 왜 임베딩 모델을 바꿨나

저장된 벡터와 실행 중 질의 벡터는 같은 모델이어야 하는데, 로컬 `bge-m3`(1.2GB)는 Render 무료 512MB에 안 올라가고 호스팅 `baai/bge-m3`는 지원 종료(HTTP 410)였다. 그래서 9,155건 전체를 `nvidia/nemotron-3-embed-1b`로 다시 임베딩했고(287요청, 약 12분 30초, 실패 0), 2048차원을 Matryoshka 성질대로 앞 1024개만 잘라 스키마·HNSW 인덱스를 그대로 뒀다. LOO 산미 ±1은 0.75 → 0.735로 동점 잡음(±1~3%p) 안이었고, 한국어 질의 "고소하고 초콜릿 같은 브라질"은 오히려 top5가 모두 초콜릿·견과 노트 원두로 나아졌다. 원자료: [ADR 0003](adr/0003-embedding-model.md), [embedding_sanity_ko.json](../data/eval/embedding_sanity_ko.json).

### 10. 왜 이웃 정렬을 결정적으로 만들었나

같은 데이터·같은 대상인데 재적재할 때마다 LOO가 1~3%p씩 움직였다. 원인은 CQI 1,546개 중 744개가 임베딩이 완전히 같은 쌍둥이라 동점이 많고, 동점 안의 순서가 행의 물리적 저장 순서에 좌우됐기 때문이다. `ORDER BY embedding <=> v, id`로 id를 2차 키로 넣자 두 번 돌린 LOO 결과 JSON의 sha256이 같아졌다. HNSW 인덱스는 그대로 타고(`Incremental Sort`만 추가), 지연은 47.97 → 48.33ms(+0.7%)로 잡음 안이다. 원자료: [ADR 0006](adr/0006-deterministic-neighbors.md), [phase2_loo_repro.json](../data/eval/phase2_loo_repro.json).

### 11. 왜 설명 품질을 판정자 두 명으로 재나

지연만 재서는 "설명이 사실과 맞는가"를 알 수 없어, 손으로 쓴 24케이스에 결정적 규칙 검사(외국어·길이·숫자 근거·조건 언급·극성)와 LLM 판정자 두 명을 붙였다. 판정자가 하나면 그 모델의 성향이 곧 점수가 되고, 1차의 judge2는 생성 모델과 같은 nemotron이라 진짜 모순(산미 3 원두를 산미 4.5 손님에게 "매우 잘 맞는다")을 놓쳤다. 그래서 합격은 두 판정자가 모두 문제없다고 할 때만 세고, 2차에서 judge2를 다른 벤더(`gpt-oss-20b`)로 바꿨다. 2차 결과는 규칙 통과 10/22 → 18/24(재채점; 재채점 전 21/24), 모순 없음 두 판정자 합의 17/22, 폴백 0/24다. 원자료: [ADR 0005](adr/0005-explain-quality-eval.md), [phase2_explain_quality.json](../data/eval/phase2_explain_quality.json).

### 12. 데이터 라이선스는 어떻게 정했나 (전체판과 오픈판)

가장 큰 소스인 coffeereview(Kaggle 스크랩, 약 7.4천 건)는 원 저작권이 Coffee Review에 있어 비상업 포트폴리오 용도로만 쓰고 원본은 레포에 넣지 않았다. 대신 그 데이터를 뺀 오픈 라이선스판을 평가(`exclude_sources`)와 배포(https://coffee-sommelier-open.vercel.app) 양쪽에 따로 만들어, 공모전처럼 라이선스가 엄격한 곳에 낼 수 있게 했다. 대가는 수치로 드러난다: 원두 9,155 → 1,655개, LOO 산미 ±1 0.735 → 0.5126(n=199), 디카페인 168 → 6개. 국내 로스터리 5곳의 사실 정보(설명 문구 미저장, robots.txt 준수)를 더하면 디카페인이 6 → 13개로 늘어, 한국에서 살 수 있는 디카페인 후보가 처음 생긴다. 프랜차이즈 추천(조건 위반 0/108, 이디야 메뉴 추가 전 0/102)은 메뉴 데이터만 쓰므로 두 판이 같다. `compare3`(전체/오픈/오픈+로스터리를 CQI 200개 고정 대상으로 비교하던 지표)는 산미는 그대로 0.495로 재나(LOO 대상 게이트를 산미 하나만 요구하도록 고쳐 CQI 200개가 재라벨 전과 동일하게 뽑힌다), 바디는 CQI 200개 전원이 결측이라 정확도 자체가 없다(n=0, 15번). 원자료: [phase2_loo_open.json](../data/eval/phase2_loo_open.json), [phase2_compare3.json](../data/eval/phase2_compare3.json).

### 13. 왜 향미 태그 예측을 학습형 모델로 바꿨나

이웃 투표(lift 게이트 포함, ADR 0007)의 LOO 태그 F1은 0.3974(n=168)로 계속 가장 약한 지표였다. 스파이크
([docs/spikes/2026-09-27-tag-model-spike.md](spikes/2026-09-27-tag-model-spike.md))에서 같은 1024차원
임베딩 위에 MLP(1024→128→54, 다중 라벨)를 학습시켰더니 F1이 크게 뛰었지만, `pipeline/embed.py`가 원두
자기 자신의 `flavor_tags`를 그 원두의 저장 임베딩 텍스트에 이미 넣고 있어서(정답이 입력에 들어있는
누수) 그 수치를 그대로 믿을 수 없었다. 그래서 학습·평가 양쪽 다 태그를 뺀 텍스트로 다시 임베딩했다
(`embedding_text(..., include_tags=False)`, query 모드, 7,327건·238요청) — `app/graphs/analyze_bean.py`가
실제로 임베딩하는 사용자 입력 텍스트도 태그가 없으니, 이제 학습·운영 입력의 분포가 같다. 결과: 고정 200개
중 태그 보유 168개를 **같은 누수 없는 질의 임베딩**으로 채점하면 이웃 투표 F1 0.3695 vs 학습 모델 F1
**0.7329**(카테고리 F1 0.6298 → 0.8292) — 학습에서 완전히 뺀 국내 로스터리 태그 39건(한국어 노트 기반,
coffeereview 출처 아님)에서도 학습 모델이 이웃 투표를 이긴다(F1 0.434 vs 0.249). 학습 라벨이
coffeereview 파생이라 오픈 데이터판(`DATA_VARIANT=open`)에는 이 모델을 올리지 않고 이웃 투표만 쓴다.
가중치는 1.24MB(2MB 예산 이내), 순수 파이썬 순전파는 호출당 7.1ms(50ms 예산의 15%). 원자료:
[ADR 0008](adr/0008-learned-tag-model.md), [phase2_tag_model.json](../data/eval/phase2_tag_model.json),
[phase2_loo.json](../data/eval/phase2_loo.json).

### 14. 왜 속성 예측(산미/바디/단맛)도 학습형 모델로 바꿨나

13번과 같은 논리를 속성에도 적용했다: `predict_from_neighbors`의 나머지 절반(산미·바디·단맛)도 여전히
이웃 가중 평균이었다. `scripts/train_attr_model.py`가 속성마다 릿지 회귀와 작은 MLP(1024→128→1)를
5-fold CV MAE로 비교해 독립적으로 고른다. 학습 풀은 태그 모델과 같은 태그 프리 임베딩이고, 대상에서
뺀 고정 200개도 동일하다 — 이번엔 CQI(사람 커핑, 태그 없음)도 학습에 포함시켜서 태그 프리 캐시를
CQI까지 확장했다(약 1,600건 추가). 결과(같은 누수 없는 임베딩으로 재면): 산미 MAE **0.6233** vs 이웃
0.7325(n=200) · 바디 **0.6706** vs 0.8709(n=153) · 단맛 **0.4406** vs 0.5653(n=99) — 세 속성 모두
학습 모델이 이웃 평균을 이긴다. 바디를 무게감으로 재라벨링하면서(15번, ADR 0010) 학습 표본이
8,798건 → 6,436건으로 줄었지만(CQI 결측 + 무게감 언급 없는 리뷰) 오히려 MAE·±1 둘 다 좋아졌다 —
산미·단맛은 이번 재라벨의 영향을 받지 않아 최초 수치(ADR 0009)와 사실상 같다. 오픈판은 CQI + 국내
로스터리 + shopify만으로 따로 학습했는데, 표본이 훨씬 작아 산미는 이제 진짜 200개짜리 held-out(재라벨
전과 동일 대상)에서도 모델이 이웃 평균보다 MAE·±1 둘 다 나쁘고(1.14/0.45 vs 1.1004/0.48), 바디는
학습 표본이 CQI 결측으로 1,379건 → 31건으로 무너져 최소 기준(300건) 미달이라 둘 다 탑재하지 않는다
(오픈판은 이제 세 속성 모두 이웃 평균만 쓴다, 15번). 향미 카테고리(SCA 7대 분류)로 오픈판 태그
모델도 시도했지만(측정 풀 145건), CV 카테고리 F1(0.6459)이 이웃 투표(0.6593)를 못 넘어 탑재하지
않았다 — 표본이 너무 작아 전체 카탈로그를 이웃으로 쓰는 투표를 이기지 못한다. 가중치는 전체판
1.2MB(gzip 불필요), 순전파는 13.8ms/호출.

**재학습은 "좋아진 속성만" 교체한다(2026-09-28).** 국내 로스터리가 공개한 산미·바디·단맛 게이지가
들어오면서(로스터리 209건, 산미 라벨 +96) 같은 고정 200개(`--pin-holdout`)로 다시 학습해 비교했다:
산미 MAE 0.6272 → **0.6211**(±1 0.81 → 0.83)만 좋아져 산미 회귀기만 바꿨고, 바디(0.6695 → 0.6740)와
단맛(0.4407 → 0.4459)은 나빠져 기존 가중치를 그대로 뒀다. 태그 모델은 로스터리가 태그 학습 풀에서
빠져 있어 학습 데이터가 같고 held-out F1도 0.7329로 같아 교체하지 않았다. 표본을 늘렸다고 무조건
교체하지 않는 건, 같은 대상·같은 임베딩으로 잰 수치가 나빠지면 "데이터를 더 넣었다"는 이유만으로는
운영 품질이 좋아진다는 근거가 없어서다([phase2_retrain_2026-09-28.json](../data/eval/phase2_retrain_2026-09-28.json)).
원자료: [ADR 0009](adr/0009-learned-attribute-model.md), [ADR 0010](adr/0010-body-heaviness.md), [phase2_attr_model.json](../data/eval/phase2_attr_model.json), [phase2_attr_model_open.json](../data/eval/phase2_attr_model_open.json), [phase2_tag_model_open_feasibility.json](../data/eval/phase2_tag_model_open_feasibility.json).

### 15. 왜 바디를 무게감으로 다시 라벨링했나

coffeereview·CQI의 "body" 컬럼은 무게감(라이트~헤비)이 아니라 큐핑 **품질** 점수였다 — 그걸 그대로
5분위화해 쓰다 보니 원산지별 평균이 실제와 반대로 나왔다(가벼운 에티오피아 3.90 > 무거운 인도네시아
3.22, 습식 탈각으로 유명한 헤비바디 만델링이 2.40으로 카탈로그 중앙값 근처). `scripts/relabel_body.py`가
리뷰 원문에서 mouthfeel/body/texture 문장을 뽑아 LLM(`judge_explain2`, gpt-oss-20b)으로 1(라이트)~
5(헤비) 무게감을 다시 매겼다(coffeereview 7,392건, ~740 요청; 무작위 스팟체크 20건 중 19건 ±1 이내
일치). CQI는 재판단할 리뷰 원문이 없어 바디를 결측(`None`)으로 비웠고, roasters_kr은 노트 단어 규칙
(묵직/무거운/풀바디 → 4, 가벼운/라이트/깔끔한 바디 → 2)으로 채운다. 결과: 인도네시아 3.21 > 케냐 3.14
> 에티오피아 3.09 > 브라질 2.97(원산지 평균이 뒤섞인 값이라 브라질만 예상보다 낮다), 만델링 2.40 →
3.50. 학습 모델은 재라벨 후에도 이웃 평균을 이긴다(바디 MAE 0.6706 vs 0.8709, ±1 이내 0.7778 vs
0.634).

**LOO 대상 게이트도 함께 고쳤다.** CQI 바디가 전부 결측이 되면서, 기존처럼 "산미 AND 바디 둘 다
not null"을 요구하면 CQI가 대상 후보에서 통째로 사라져 산미조차 잴 수 없었다(`compare3`가 한때
그랬다). `app.repo.Repo.random_coffee_ids_for_loo`의 게이트를 **"산미만 not null"**로 좁히자
(바디·단맛은 `loo_accuracy`가 각 속성 truth가 있는 대상만 따로 세어 자기 몫의 n을 보고한다), 대상
200개(시드 42) 자체가 **재라벨 전과 정확히 같은 집합**으로 복원됐다 — 그래서 위 14번의 산미 수치가
ADR 0009와 사실상 동일하고, `compare3`의 산미 ±1도 다시 0.495로 재라벨 전과 같다. 대신 바디는 그
동일한 200개 중 실제로 무게감이 있는 153개로만 채점되고(n=153), `compare3`는 대상 소스가 CQI
하나뿐이라(CQI 200개 전원 결측) 바디 정확도 자체가 없다(n=0 — 12번). 오픈판 속성 모델은 바디 학습
표본이 1,379건 → 31건으로 무너져 최소 기준(300건) 미달로 탑재를 중단했다(오픈판은 이제 세 속성 모두
이웃 평균만 쓴다).
원자료: [ADR 0010](adr/0010-body-heaviness.md), [phase2_attr_model.json](../data/eval/phase2_attr_model.json), [phase2_compare3.json](../data/eval/phase2_compare3.json).

### 16. 무엇이 안 됐나

- **오픈판 향미 카테고리 모델은 표본 부족으로 기각했다.** 측정 풀 145건으로는 이웃 투표(전체 9천여 건을
  이웃으로 씀)를 카테고리 F1에서 넘지 못했다(0.6459 vs 0.6593, 14번). 오픈판은 향미 태그를 계속 이웃
  투표로만 낸다.
- **`compare3`의 CQI 고정 200개 LOO 방식은 바디를 잴 수 없다.** 바디 재라벨(15번, ADR 0010)로 CQI
  바디가 전부 결측이 되어, 대상 소스가 CQI 하나뿐인 이 지표는 산미(0.495, 재라벨 전과 동일)는 그대로
  재지만 바디는 정확도 자체가 없다(n=0) — 국내 로스터리 데이터가 바디 예측에 기여하는지는 이 방식으로
  잴 수 없다. 확실한 기여는 커버리지(디카페인 6 → 13)뿐이다([phase2_compare3.json](../data/eval/phase2_compare3.json)).
- **설명의 환각은 절반만 줄었다.** 규칙 통과는 18/24(재채점 전 21/24)지만 두 판정자가 모두 환각 없음으로 본 건 14/22다. 남은 환각은 "균형이 좋아요" 같은 평가적 수사와 1~5 수치를 "보통"으로 뭉개는 버릇이다([ADR 0005](adr/0005-explain-quality-eval.md)).
- **메뉴는 10개 브랜드 중 8개만 실측이다.** 이디야는 robots.txt가 막는 "더보기"(`/inc/`)를 부르지 않고 서버가 그리는 첫 카드만 검색어로 모아 41종이다([ADR 0014](adr/0014-public-sources-ediya-twosome-kca-zenodo.md)). 투썸(메뉴 봇 차단)·블루보틀(음료 메뉴 미공개)은 브랜드 원두 카드만 나온다.
- **운영 통계는 아직 비어 있다.** 텔레메트리와 집계 스크립트는 붙였지만 첫 집계 구간의 요청이 0건이라 운영 폴백 비율은 수동 스모크(2/18)밖에 없다([prod_stats_2026-09-26.json](../data/eval/prod_stats_2026-09-26.json)).
- **3단계(사진 스캔·Vision)와 4단계(멀티턴 에이전트)는 착수하지 않았다.** Lighthouse 12는 PWA 항목을 없애 설치 가능성은 수동으로만 확인했다([lighthouse.md](screenshots/lighthouse.md)).

### 17. 왜 오픈판 속성 예측에 로스터리 게이지와 특징 모델을 썼나

오픈판(공모전 제출본)의 산미 라벨은 대부분 CQI 커핑 **품질** 점수의 5분위라 "얼마나 신가"가 아니었고,
바디는 15번 재라벨 이후 CQI 전원 결측이라 이웃 평균이 강도를 배울 재료가 없었다. 그런데 국내 로스터리
4곳(커피 리브레·1킬로커피·G로스팅·내일의커피)이 상품 페이지에 자기 원두의 맛 게이지(점·막대·숫자)를
직접 공개한다 — 로스터가 매긴 **사람 라벨**이고 페이지의 사실 표기다. HTML/텍스트 게이지만 읽어(이미지는
읽지 않음) 82건(산미 82·바디 64·단맛 72)을 1~5로 정규화하고, `coffees.attr_label_source`에 라벨 출처를
속성별로 남겼다. LLM 추정을 예측기로 쓰지 않는 대신 산지·고도·가공·로스팅·품종·디카페인 공정·노트 단어
범주로 된 **해석 가능한 리지 회귀**를 학습했다. **로스터리 단위 교차검증**(한 로스터리는 학습·평가
한쪽에만)에서 산미 ±1 0.658 vs 오픈 이웃 평균 0.500, 단맛 0.569 vs 0.514로 탑재 기준(+0.05)을 넘었고,
바디는 0.797 vs 0.750(+0.047)으로 미달이라 이웃 평균을 유지한다. 선형 모델만 싣는 이유는 예측을 특징별
기여도로 풀어 "과일 노트·고지대(1,900m)·약배전 → 산미↑" 같은 근거 문장을 붙이기 위해서다(GBT는 비교용).
우선순위는 문구 단서 > 특징 모델 > 이웃 평균. 라벨이 4개 로스터리뿐이라 로스터리별 척도 관행 차이가 오차의
큰 몫이고, 단맛 개선은 72건 중 4건 차이다.
이후 산미는 노트 단어 약한 라벨을 더한 모델로 바뀌었다(19번).
원자료: [ADR 0011](adr/0011-roaster-gauges-feature-model.md), [phase3_feature_model.json](../data/eval/open/phase3_feature_model.json)

### 18. 프랜차이즈 원두 값은 어디서 오나

프랜차이즈 카드의 산미·바디·단맛·향미는 원래 뉴스 기사와 메모를 보고 손으로 고른 값이었다. 이제는 각 브랜드 공식
사이트에서 매장 음료에 쓰는 원두의 공식 설명(이름·로스팅·블렌드·맛 문구 원문)을 robots.txt를 지켜 모으고
(`data/curated/brand_beans_official.yaml`), 그 문구를 **처음 보는 원두와 같은 경로**(태그 프리 쿼리 임베딩 → 전체판
학습 모델, 문구에 직접 쓰인 "묵직한 바디"·"상큼한" 같은 단서가 모델보다 우선)에 넣어 값을 만든다. 값마다 출처를
`official_gauge | official_notes_model | estimate`로 남기고, 카드 근거 줄에는 공식 문구 한 줄이 그대로 나온다.
20개 원두(10개 브랜드 × 하우스/디카페인) 중 14개가 공식 맛 설명을 얻었고(투썸 2개는 커피이야기 페이지를 손으로 옮겨 추가),
6개(컴포즈 설명 없음 등)는 추정을 유지했다. 게이지는 투썸의 산미·바디 막대(%)가 유일해 1~5로 환산해 그대로 쓴다
(ADR 0014). 조건 위반은 0/102 그대로(이디야 메뉴 추가 후 0/108), 페르소나 4명의 브랜드별 상위 3개
메뉴 다양성(서로 다른 이름 27/24/27/24)도 그대로다. 향미 태그는 모델보다 브랜드가 직접 쓴 단어를 우선한다 —
마케팅 문구는 학습 분포(영어 리뷰·로스터리 노트) 밖이라, 브랜드가 쓰지 않은 "체리" 같은 태그를 카드에 붙이지 않으려고.
원자료: [ADR 0012](adr/0012-official-brand-beans.md), [brand_beans_derived.json](../data/eval/brand_beans_derived.json).

### 19. 라벨을 세 갈래로 더 넣었는데 왜 산미만 바꿨나

공모전은 데이터 레시피로 겨루니, 특징 모델을 LLM으로 바꾸지 않고 **라벨을 늘려서** 이기는지 시험했다. (A) 해외 Shopify
로스터 8곳이 자기 원두에 붙인 강도 표기("VIBRANT & BRIGHT", "Low Acid", "Body: full") 199건을 한 사전으로 1~5 환산,
(B) 원두 자기 노트 단어를 고정 사전으로 산미·바디·단맛 약한 라벨로(192건), (C) 로스터별 척도 오프셋. 평가는 ADR 0011과
같은 게이지 82건·로스터리 단위 CV이고, 추가 라벨은 학습 쪽에만 넣었다. 산미는 B(약한 라벨을 게이지 수준으로 재중심,
가중치 0.3)가 ±1 0.658→**0.695**, MAE 0.923→0.771로 탑재 기준(+0.03)을 넘었고 가중치·이웃 풀·출처를 바꿔도 유지돼
교체했다. A는 처음엔 0.768로 가장 좋아 보였지만 가중치가 "고도 네 구간 모두 +"였다 — 고도를 적는 가게(Kiss the Hippo)는
밝게, 안 적는 가게(Volcanica·Intelligentsia)는 낮게 표기해서 모델이 **페이지 형식을 산미로 배운** 것이다. 고도를 가리면
이득이 사라져(0.646) 쓰지 않았다. 단맛의 약한 라벨 이득(+0.069)은 재중심하면 사라지는 수준 이동이었고, 바디는 약한 라벨이
산지 평균을 못 이겨(0.68 동률) 미리 정한 게이트대로 쓰지 않았다. C는 폴드당 게이지 로스터리가 3곳뿐이라 도움이 안 됐다.
원자료: [ADR 0013](adr/0013-open-labels-weak-supervision.md), [phase4_open_labels.json](../data/eval/open/phase4_open_labels.json)

### 20. 데이터는 어떻게 최신으로 유지하나

메뉴와 원두는 계절마다 바뀌는데, 운영 DB에는 사용자 기록이 있어 덤프로 통째로 덮을 수 없다. 그래서 주 1회 GitHub Actions가
메뉴 8개 브랜드와 로스터리 원두를 robots.txt를 지켜 다시 모으고, 운영 카탈로그를 스테이징 DB로 복제한 뒤 **바뀐 것만** 다시
보강·임베딩한다(나머지는 DB 행을 그대로 재사용). 게시 전에 두 판 모두에서 조건 위반 0, LOO 산미가 기준선에서 0.02 넘게
떨어지지 않음, 한 번에 20% 넘게 사라지지 않음(스크레이퍼 고장 신호), README 수치 재생성·대조, 전체 테스트를 통과해야 하고,
통과하면 카탈로그 표의 바뀐 행만 키 기준으로 운영 Neon에 옮긴다(사용자 표는 건드리지 않는다). 사람이 우유 여부를 판단하지
않은 새 메뉴는 닫힌 쪽으로 — 적재는 하되 라벨을 달 때까지 추천하지 않는다. CI에는 로컬 LLM이 없어 보강은 호스팅 모델로
하는데, 로컬 모델과 같은 원두 50개에서 속성은 둘 다 값을 내면 ±1 안에서 모두 일치했고(태그 F1 0.66), 호스팅 모델이 "근거
없음" 대신 값을 내는 경우가 약 4분의 1이라는 차이를 기록해 두었다. 모델 재학습은 월 1회 후보만 만들고 지표가 좋아질 때만
PR을 연다 — 모델 교체는 자동으로 병합하지 않는다.
원자료: [ADR 0015](adr/0015-automated-refresh.md), [enrich_ci_agreement.json](../data/eval/enrich_ci_agreement.json),
[샘플 리포트](ops/refresh-sample-report.md)

### 21. RAG인데 왜 LLM에게 검색 결과를 그대로 주지 않나

**검색한 사실을 코드가 먼저 문장 조각으로 바꾸고, LLM은 그 조각 안에서만 문장을 잇게 한다.** 검색(pgvector 이웃, SQL 조건
필터)은 맞게 했는데 LLM이 그 사실을 해석하다가 틀리는 것이 이 앱 설명 오류의 대부분이었다. 처음에는 "음료 2 · 손님 4.5"
같은 숫자를 주고 비교를 맡겼더니 "산미가 선호보다 높아요"(실제로는 낮음) 같은 방향 오류가 나왔고, 두 판정 모델이 모두
모순 없다고 본 설명은 17/22였다. 그래서 해석을 한 단계씩 코드로 옮겼다: 속성마다 "선호와 비슷함 / 조금 강함 / 훨씬 약함"
(3차, 20/22), 맞는 점·아쉬운 점 목록(4차, 22/23 — 차이를 적합의 이유로 대는 결론 오류 8/40 → 0/40), 음료 맛 한 줄과
적합도별 추천 문구(5차, 23/23 · 오픈판 23/23, "전체적인 균형" 같은 빈말 2/23 → 0/23, 도움 4.13 → 4.39/5).

조각은 **그대로 옮겨도 맞는 문장**이어야 한다. "산미: 강함" 같은 라벨을 줬더니 LLM이 라벨을 문장에 그대로 옮겨 검사 전
규칙 통과가 16/23 → 6/21로 떨어졌고, "산미가 적당한 음료지만 선호보다 조금 강한 산미"처럼 절대·상대 표현을 나란히 주면
둘 다 사실인데도 모순으로 읽혔다(22/23 → 16/20). 그래서 선호와 가까운 속성은 음료 자체 표현("바디가 중간 정도"), 먼
속성은 선호 대비 표현("산미가 선호보다 조금 강하고")으로 한 줄을 만든다. LLM이 조각 밖으로 나가면(숫자와 반대 방향,
차이를 이유로 든 결론, 내부 필드명) 규칙 검사가 정해진 틀 문장으로 바꾸고, 댈 이유가 없는 카드는 LLM을 부르지 않는다.
결과적으로 LLM 원문이 검사 전에 이미 규칙을 지킨 비율이 17/24 → 23/23이 됐다 — 품질이 사후 수정이 아니라 입력
설계에서 나온다. 그래도 LLM을 빼지 않은 이유는 조각을 손님 상황에 맞게 잇는 일(무엇을 첫 이유로 들지, 위반을 어떻게
먼저 말할지)이 여전히 남아 있기 때문이다. 24케이스에서 LLM이 이은 설명의 도움 점수는 4.5·3.4(오픈판 4.55·3.5),
코드만 쓴 설명(맞는 점이 없는 3건)은 3.67·2.67(4.0·3.0)이었다 — 다만 코드만 쓴 건은 원래 추천하기 어려운 카드라 같은
조건의 비교는 아니다.

[open/phase2_explain_quality.json](../data/eval/open/phase2_explain_quality.json)
