# ADR 0005 — 설명 품질 평가: 24케이스 × 규칙 검사 × LLM 판정자 2개

- 상태: 채택 (2026-09-27)

## 맥락
추천 카드의 설명은 LLM(`explain` = nemotron, thinking 끔)이 스트리밍으로 만든다. 지금까지는 지연(ADR 0004)만 쟀고,
"설명이 사실과 맞는가, 쓸모 있는가"는 사람이 눈으로 몇 개 본 것이 전부였다. 프롬프트나 모델을 바꿀 때 품질이 좋아졌는지
나빠졌는지 말할 수 있는 고정된 잣대가 필요하다.

## 결정
`uv run python -m app.eval explain_quality` (LLM 호출 약 72회라 `all`에는 넣지 않음) → `data/eval/phase2_explain_quality.json`.

1. **케이스 세트** `data/eval/explain_cases.yaml` — 손으로 쓴 24개. 가상 페르소나 4(`app.eval.PERSONAS`) × 항목 유형 4
   (메뉴 실측 / 브랜드 원두 추정 / DB 원두 / 예측 원두) = 16, 조건 위반 4, 극단 점수 4(≤0.35 두 개, ≥0.95 두 개).
   `score`는 `score_item`이 실제로 주는 값, `violation`은 `passes`의 실제 문구로 맞췄다(케이스 작성 시 대조). 개인 데이터 없음.
   '제한없음' 페르소나는 조건 위반이 원천적으로 불가능해 위반 케이스 하나를 '디카페인+우유X+단맛'에 더 넣었다.
2. **생성** — 운영과 같은 경로: `explain_messages` → `astream_text("explain")`, 12초 마감, 실패하면 운영과 똑같이
   `template_explanation`으로 폴백(폴백도 결과로 기록하되 품질 수치는 LLM 생성분만으로 계산).
3. **규칙 검사**(결정적, `app/core/explain_check.py`) — 외국어, 2문장·220자 이내(재채점 전에는 3문장), 숫자 근거, 조건 위반 언급, 극성(첫 문장 기준).
4. **판정자 2개** — `judge`(deepseek-v4.1-flash)와 `judge2`(1차 nemotron-3-super + `enable_thinking: false` → 2차부터 별도 태스크 `judge_explain2` = `openai/gpt-oss-20b`, 아래 "2차 변경"; 결과 JSON에서는 계속 `judge2` 칸)에
   페이로드 사실 + 설명을 주고 `{contradiction, hallucination, helpful 1~5}` JSON(`app/core/judge.py`). 잘못된 JSON·타임아웃은
   3회까지 재시도, 끝내 실패하면 null로 남기고 두 판정자 합의 수치에서 뺀다.

판정자 선택: 1단계 골드셋에서 이미 쓰던 두 태스크를 그대로 쓴다(서로 다른 벤더 → 한쪽 편향 견제). judge2는 생성 모델과
같은 nemotron이라 "자기 글 채점" 편향이 있을 수 있어, 합격 수치는 **두 판정자 모두** 문제 없다고 한 경우만 센다.
24개라 Cohen κ는 불안정해 단순 일치율을 쓴다.

### 들여다본 사례
- **판정자 불일치 — 진짜 모순을 nemotron이 놓침** (`bluebottle_brandbean_decaforder_mid`, 산미 4.5 선호 손님 × 산미 3·단맛 4 원두):
  「산미와 단맛 수치가 손님 선호도와 매우 잘 맞으며 … 과일과 꽃 향미가 아닌 바닐라 및 카라멜라이즈드 향이 주를 이루므로」.
  deepseek은 모순(산미 3 vs 4.5, 향미에 lime이 있는데 과일이 아니라고 단정)으로 잡았고 helpful 2를 줬다. nemotron(생성 모델과 동일)은
  모순 없음·helpful 4. 두 판정자 합의를 요구한 이유가 이 케이스다.
- **외국어 섞임 + 사실 오독, 판정자는 절반만 잡음** (`db_not_decaf_brazil_violation`): 「… 우유 불가 조건에도 우유 사용 여부가
  명시되지 않아 조건에 위배됩니다. 단맛 5와 바디 4는 … parcialmente 일치하지만」. 포르투갈어 `parcialmente`는 규칙 검사가 잡았다.
  페이로드에 `우유: false`가 있는데 "명시되지 않았다"는 오독은 judge2가 모순으로 보지 않았고 judge는 타임아웃(null)이었다.
- **두 판정자 모두 환각으로 합의** (`db_decaf_huehuetenango_top`): 「단짠한 향미까지 갖추고 있어 추천드립니다」 — 향미는 흑설탕·캐러멜·꿀뿐,
  짠맛은 없다. 규칙 검사로는 잡을 수 없는 종류(숫자·외국어 아님)라 판정자가 필요한 이유.
- **"unknown" + 사실과 다른 조건 설명** (`predicted_antigua_caffeine_violation`): 「카페인 조건 위반(저카페인 선호인데 디카페인 여부 unknown)」
  — 영어 단어(규칙), 페이로드는 `디카페인: false`(두 판정자 모두 환각). 점수 86인데 "맞지 않을 수 있습니다"라고 써서 극성 규칙도 실패
  (조건 위반이 있을 때 높은 점수와 부정 결론이 공존하는 건 오히려 맞는 동작이라, 극성 규칙은 위반 케이스에서 느슨하게 봐야 한다).
- **폴백 템플릿 자체의 문제** (`twosome_brandbean_decaforder_high`): 「… 디카페인으로 변경해서 주문하세요 (+200원).」 — 두 판정자 모두
  "+200원은 사실에 없음"(환각), deepseek은 "이미 디카페인인데 변경하라고 함"(모순). 원인은 코드 쪽이다: 페이로드의 `디카페인`이
  `is_decaf or order_decaf`로 합쳐져 "원래 디카페인"과 "디카페인으로 바꿔 주문"을 구분하지 못하고, `decaf_surcharge_krw`는
  템플릿에만 있고 페이로드에는 없다. 템플릿은 "취향 적합도 84%."처럼 마침표로 끊겨 4문장이 되어 길이 규칙도 넘는다.

### 읽은 것
- 가장 흔한 실패는 **길이**(10/22): 시스템 프롬프트는 "2문장 이내"인데 모델이 4~5문장을 쓴다. 다음 프롬프트 개선 1순위.
- 모순은 드물고(합의 기준 2/21), 환각은 대부분 "균형이 적절하다", "풍부한 향" 같은 평가적 수사다. deepseek이 이를 엄격하게
  환각으로 잡고 nemotron은 관대해서 환각 일치율이 57%에 그친다 — 환각 수치는 판정자 성향에 크게 좌우되므로 모순 수치를 주 지표로 쓴다.
- 조건 위반 4건은 모두 설명에 위반이 언급됐다(규칙 `condition_mentioned` 0 실패).

## 2차 변경 (1차 결과로 고친 것)
1차에서 드러난 결함을 고치고 같은 24케이스를 다시 돌렸다.

- **페이로드 디카페인 분리** — `디카페인`(= `is_decaf or order_decaf`)을 `디카페인 음료` / `디카페인으로 주문 권장`으로 나누고
  `디카페인 추가요금(원)`(주문 권장일 때만, 없으면 null)을 넣었다. 프롬프트: "디카페인 음료가 true일 때만 디카페인이라고 말하고,
  주문 권장이면 '디카페인으로 바꿔 주문하면 (+N원)'".
- **템플릿 2문장** — 점수를 첫 문장에 합치고(「취향 적합도 84%로 산미·바디가 선호와 가까워요.」) 향미·디카페인 주문·예측 신뢰도는
  `·`로 이어 한 문장. 위반은 「주의: … — 」로 첫 문장 앞에 붙인다.
- **규칙 검사 보정** — 문장 분리에서 숫자 사이 마침표(4.5)는 끊지 않고, 한글 음절이 없는 조각(「(84%)」)은 문장으로 세지 않는다.
  조건 위반이 있으면 극성 검사를 하지 않는다(점수가 높아도 부정 결론이 맞는 답).
- **길이 강제** — 시스템 프롬프트 맨 끝에 하드 규칙(`length_rule`): "줄바꿈 없는 한 문단, 최대 2문장. 세 번째 문장·괄호 메모·고쳐 쓴
  두 번째 답 금지, 향미 이름 말고는 한국어만, 항목 이름·true/false 옮기지 말 것" + 숫자 없는 2문장 예시. 조건 위반이 있으면 첫 문장에
  위반과 "주문 전 확인" 결론을 함께 쓰라고 이 규칙 안에 넣었다(앞쪽 위반 규칙만 두면 뒤의 예시에 밀려 위반을 빠뜨렸다).
  `explain.max_tokens` 1500 → **220**. 탐침 약 20회(폭주 케이스 포함): 모두 `finish_reason: stop`, 40~142토큰(프롬프트 수정 전
  자기수정 문단까지 쓴 최악 케이스도 209) — 문장 중간 잘림 없음이라 300으로 올리지 않았다. 다만 nemotron은 온도 0.3에서 같은

### 읽은 것 (2차)
- **길이는 해결** — 규칙 통과 10→21 중 4건은 검사기 보정(소수점·극성) 몫이고 7건이 생성 개선 몫이다. 길이 실패는 0이지만
  3문장 설명이 3개 남아 있다(당시 검사 한도가 3문장이라 통과 — 아래 "재채점"에서 2문장 한도로 실패 처리).
- **환각이 줄었다**(deepseek 기준 10→14/22). 짧아지면서 "풍부한 향" 같은 수사를 덧붙일 자리가 줄었다. 남은 환각도 대부분
  평가적 수사(「전체적인 균형이 좋아요」, 「조화롭게 느껴져」)와 향미 연결 과장(「과일과 꽃 향을 떠올리게」 — 실제 향미는 vanilla·caramelized·lime).
- **새 판정자가 새 종류의 모순을 잡는다** — gpt-oss와 deepseek 둘 다 「산미·바디·단맛이 모두 보통 수준」(실제 2·4·2)을 모순으로 잡았다
  (`coffeebean_menu_mocha_blended_mid`, `ediya_brandbean_latte_high`). 생성 모델이 1~5 음료 수치를 "보통"으로 뭉개는 경향 — 다음 개선 후보.
  1차 nemotron-judge2는 모순을 한 번도 잡지 않았다(22/22 모순 없음); gpt-oss는 20/24.
- **디카페인 오독은 사라졌다** — 템플릿 폴백의 「+200원 환각」「이미 디카페인인데 바꾸라고」 사례가 없어졌고, 「디카페인으로 바꿔 주문하면 (+200원)」이
  그대로 나온다. 단 `twosome…`에서 「디카페인으로 주문 권장이 true이므로」처럼 항목 이름·true를 옮기는 버릇이 한 번 남았다(외국어 규칙이 잡음).
  `ediya_brandbean_decaforder_high`의 「디카페인으로 바꿔 주문하면 카페인 조건도 충족」은 사실과 맞는데 gpt-oss가 "디카페인 음료가 false인데
  디카페인이라 함"으로 오판했다 — 판정자 쪽 오류.
- **조건 위반 언급 1건 실패** (`predicted_antigua_caffeine_violation`): 「적합도는 86점으로 높습니다 … 취향에 잘 맞으며」 — 위반(카페인 100mg 초과/불명)을
  말하지 않았다. 탐침에서는 위반을 첫 문장에 쓰던 케이스인데 온도 0.3에서 흔들렸다. 두 판정자 모두 이를 잡지 못했다(규칙 검사만 잡음).
- **극성 1건** (`paulbassett…`, 84점): 「적합도가 84점으로 낮아」 — 높은 점수를 낮다고 함 + `parcialmente`. 규칙과 deepseek(환각) 모두 잡음.
- 첫 토큰 p95가 6.22→1.37초로 떨어진 건 이번 코드 변경보다 그날 NVIDIA 지연 차이가 크다(max_tokens는 첫 토큰에 영향 없음). 전체 시간 감소(2.46→1.52초)는
  출력이 짧아진 몫이다(`bench` 순차 10.42→4.59초, ADR 0004).

## 재채점 (2026-09-27, 검사기 수정 후 — LLM 호출 없음)
리뷰에서 검사기가 제품 규칙보다 느슨하거나 틀리게 채점하는 곳을 고쳤다(`app/core/explain_check.py`):
문장 한도 3 → **2**(제품 규칙과 같게), 극성은 **첫 문장만** 보고 부정 패턴을 긍정보다 먼저 확인(「잘 맞지 않」은 부정),
「적합도…낮아/높아」도 극성 신호, 천 단위 쉼표(「+1,500원」)는 숫자 하나로, 조건 언급은 **위반된 조건의 단어**(우유 위반 → 우유,
카페인 위반 → 카페인/디카페인)를 요구. 새로 생성하지 않고 저장된 2차 설명문 24개에 새 검사기만 다시 돌렸다
(`uv run python -m app.eval explain_recheck` → `data/eval/phase2_explain_quality.json`의 규칙 필드만 갱신, 생성·판정 필드는 2차 그대로,
원래 규칙 수치는 `rules_rescored.before`).

| 항목 | 2차 (당시 검사기) | 2차 재채점 (새 검사기) |
|---|---|---|
| 규칙 검사 전부 통과 | 21/24 (88%) | **18/24 (75%)** |
| └ 실패 내역 | 길이 0, 외국어 2, 조건 언급 1, 극성 1 | 길이 3, 외국어 2, 조건 언급 1, 극성 1 |

떨어진 3건은 전부 길이 — 위에서 "검사 한도가 3문장이라 통과"라고 적어 둔 3문장 설명 3개
(`bluebottle_brandbean_decaforder_mid`, `db_not_decaf_adado_violation`, `predicted_guji_not_decaf_violation`)가 이제 실패로 잡힌다.
극성·조건 언급·외국어 실패는 같은 케이스 그대로다. 판정자 수치와 지연은 바뀌지 않는다(재채점이지 재실행이 아님).

## 한계
- 24케이스는 작다. 비율 하나가 1건에 4%p씩 움직인다.
- 판정자도 LLM이다. 1차 judge2는 생성 모델과 같은 모델이었다(2차에서 gpt-oss-20b로 교체). gpt-oss는 판정 이유를 영어로 쓰고 "디카페인으로 주문 권장"을 "디카페인이라고 주장"으로 오판한 적이 있다. judge(deepseek)는 NVIDIA 과부하로 1~2건씩 타임아웃된다.
- 생성은 온도 0.3, 1회. 같은 케이스를 다시 돌리면 몇 건은 달라진다(NVIDIA 지연 변동으로 폴백 수도 달라짐).
- 규칙 검사의 극성 어휘 목록은 단순하다(첫 문장만·부정 우선으로 보정했지만 "맞지 않을 수" 같은 완곡 표현은 여전히 부정으로 센다).

## 운영 규칙
설명 프롬프트(`app/core/explain.py`), `explain` 모델·설정, 페이로드 구성 중 하나라도 바꾸면 `uv run python -m app.eval explain_quality`를
다시 돌려 `data/eval/phase2_explain_quality.json`과 README "2단계" 표의 설명 품질 행을 갱신한다. 판정 수치만 보지 말고 새로 실패한
케이스의 원문을 읽는다(JSON에 설명 원문이 남아 있다). 검사기(`app/core/explain_check.py`)만 바꿨을 때는 LLM을 다시 부르지 않고
`uv run python -m app.eval explain_recheck`로 저장된 설명을 재채점하고, 수치를 옮길 때 재채점이라고 밝힌다.
