# ADR 0004 — 설명 모델 thinking 끔 (explain, parse_note, parse_bean)

- 상태: 채택 (2026-09-27)

## 맥락
2단계 앱의 설명(`explain`)·후기 파싱(`parse_note`)·원두 파싱(`parse_bean`) 세 태스크는 모두 `nvidia/nemotron-3-super-120b-a12b`를
쓴다(`config/models.yaml`). 이 모델은 응답 전에 기본적으로 "생각"(chain-of-thought)을 한 뒤 답하는데, 스트리밍 설명에서 첫 토큰이
나오기까지 5~20초가 걸려 운영 타임아웃(`explain` 태스크 20초, 실질적으로 12초 내 응답이 목표)을 자주 넘겼다 — 운영 폴백(로컬 Ollama로
전환) 3/8 발생. `<think>...</think>` 태그로 감싸인 생각 내용이 스트리밍 텍스트에 그대로 섞여 나오는 문제도 있었다
(`pipeline/llm.py::extract_json`은 비스트리밍 JSON 응답에서만 이를 제거한다).

## 원인
모델이 기본값으로 "thinking"을 켠 채 응답한다. NVIDIA API는 요청 본문 최상위에 `chat_template_kwargs: {enable_thinking: false}`를
받으면 생각 단계를 건너뛴다(`reasoning_effort: "none"`도 같은 효과가 있으나 출력이 더 길어짐 — 아래 실측 참고).
`app/llm.py::_payload`는 `Target.extra`를 요청 본문 최상위에 병합하는 기존 동작 그대로 이를 실어 보낸다(새 코드 없음, 설정만 추가).

## 측정 — explain (같은 설명 프롬프트로 사전 확인, 2026-09-26)
| 설정 | 첫 토큰 | 전체 응답 | 비고 |
|---|---|---|---|
| 기본값 (thinking 켬) | 10.6초 | 15.8초 | 생각 내용이 텍스트에 섞여 나옴 |
| `chat_template_kwargs: {enable_thinking: false}` | 0.67초 | 1.73초 | 같은 품질의 한국어 2문장 |
| `reasoning_effort: "none"` | 0.78초 | — | 동작은 하지만 답이 더 길어짐 → 채택하지 않음 |

## 측정 — parse_note / parse_bean (thinking on vs off, 각 입력 3회, `.superpowers/thinking_probe.py`로 NVIDIA API 직접 호출)
입력: `app/core/parse.py`의 few-shot 예문(중복 문구 1개는 한 번만 셈, 실질 9개) + `tests/app/test_parse_explain.py` 케이스 +
새 후기 5개 + 새 원두 문구 5개. 결과 전체는 `data/eval/phase2_thinking.json`.

| 태스크 | on 일치율(자기일관성) | off 일치율(자기일관성) | on↔off 다수결 일치율 | on 지연 중앙값 | off 지연 중앙값 |
|---|---|---|---|---|---|
| parse_note (n=9) | 92.59% | 92.59% | 77.78% | 4.20초 | 1.21초 |
| parse_bean (n=8) | 100.00% | 95.83% | 75.00% | 2.59초 | 1.18초 |
| **합산** | **96.29%** | **94.21%** | — | — | — |

"일치율(자기일관성)"은 같은 입력·같은 설정으로 3번 호출했을 때 다수결과 일치한 비율(온도 0에서 결정성 척도). "on↔off 다수결 일치율"은
on의 다수결 결과와 off의 다수결 결과가 완전히 같은 입력의 비율.

on↔off 다수결이 갈린 사례를 들여다보면:
- `parse_bean`에서 갈린 2건("콜롬비아 수프리모 ...", "브라질 내추럴 다크 로스트")은 모두 `is_decaf: null`(on) vs `is_decaf: false`(off) 차이뿐이다.
  `app/core/parse.py::merge_llm_parse`는 `bool(llm.is_decaf)`로 쓰므로 `None`과 `False`는 다운스트림에서 동일하게 "디카페인 아님"으로
  처리된다 — 실질적 불일치가 아니다.
- `parse_note`에서 갈린 2건은 애매한 후기("고소하고 부드러워서 좋았어요"의 body 방향, "물 탄 것처럼 밍밍했어요"에서 acidity/sweetness까지
  뽑을지)로, on 자체도 자기일관성이 100%가 아니었다(각각 66.67%) — thinking 여부보다 문장 자체의 모호함에 가깝다.

판단 기준(off의 일치율 ≥ on의 일치율 − 5%p): 94.21% ≥ 96.29% − 5%p(91.29%) → **충족**.

## 결정
- `config/models.yaml`의 `explain`, `parse_note`, `parse_bean` 세 태스크 모두 `extra: {chat_template_kwargs: {enable_thinking: false}}`를 추가한다.
- `reasoning_effort: "none"`은 채택하지 않는다(출력 길이 증가, `enable_thinking: false`가 같은 지연 개선에 품질 저하가 없음).
- 로컬 폴백(Ollama `qwen3.5:9b`)의 `extra: {reasoning_effort: "none"}`은 그대로 둔다 — 다른 모델이라 별도 판단.

2026-09-27 재측정 — 설명을 최대 2문장·`max_tokens` 220으로 줄인 뒤([ADR 0005](0005-explain-quality-eval.md) 2차): 순차 **4.59초**,
병렬 **2.03초**, 첫 토큰 0.81~0.99초, 전체 응답 1.3~1.81초. 첫 토큰은 그대로이고 출력이 짧아진 만큼 전체 시간이 줄었다.

(이 작업 도중 thinking을 끄기 전 한 번 더 측정한 중간값은 첫 토큰 4.94~20.27초, 순차 35.5초로 운영에서 보고된 폴백 문제와 일치했다 —
NVIDIA API 자체의 지연 변동성도 있어 보이나, thinking을 끄면 최악의 경우도 대체로 12초 마감 안에 들어온다.)

## 결과
- 설명 스트리밍의 첫 토큰이 12초 마감 안에 안정적으로 들어온다(0.66~1.53초). `<think>` 태그가 텍스트에 섞이는 문제도 없어진다.
- parse_note/parse_bean도 같은 설정을 추가해 지연을 줄였다(중앙값 4.2초→1.21초, 2.59초→1.18초); 파싱 정확도(자기일관성)는
  통계적으로 유의한 저하 없음(합산 96.29%→94.21%, −2.08%p, 기준 −5%p 이내).
- 여전히 드문 지연 스파이크(예: 벤치 1회차 8.02초)가 관측된다 — NVIDIA API 큐잉/콜드스타트로 보이며, 20초 타임아웃과 로컬 폴백은 유지한다.

## 되돌리는 방법
`config/models.yaml`에서 해당 태스크(`explain`/`parse_note`/`parse_bean`)의 `extra: {chat_template_kwargs: {enable_thinking: false}}`
줄을 지우면 즉시 기본(thinking 켬) 동작으로 돌아간다. 코드 변경은 없으므로(설정만 추가) 재배포만 하면 된다.

|---|---|---|---|
| 할리스 | 4.0s | 1.5s | 3 / 0 |
| 커피빈 | 2.5s | 1.0s | 3 / 0 |
| 폴바셋 | 3.6s | 1.7s | 2 / 1 |
| 컴포즈 | 9.5s | 1.1s | 3 / 0 |
| 스타벅스 | 3.8s | 1.2s | 2 / 1 |

폴백 2/18(11%; thinking 끄기 전 3/8=37%). 첫 토큰은 1~2초로 안정적이고, 남은 폴백은 NVIDIA 쪽 꼬리 지연(요청 하나가 12초 마감을 넘김)이다. 다음 후보: 첫 토큰이 4초 안에 안 오면 같은 요청을 하나 더 보내 먼저 오는 쪽을 쓰는 헤지(hedged request) — 운영 텔레메트리(ADR 0005 이후)로 폴백 원인 분포를 본 뒤 결정.
모든 카드에 실제 메뉴명이 나왔다(예: 할리스 「흑임자 버터크림 라떼」 93mg, 폴바셋 「에스프레소 마키아토」 113mg → 디카페인 변경 안내).

## 헤지 요청 (hedged request)

**왜.** 로컬 평가의 첫 토큰은 p50 0.77초 / p95 1.37초인데, 운영에서는 카드 18장 중 2~3장이 여전히 12초 마감을 넘겨 템플릿으로
폴백됐다. 원인은 모델이 아니라 NVIDIA 쪽 서버 큐잉이다 — 드물게 요청 하나가 첫 토큰까지 12초 넘게 걸리는데, 같은 요청을 다시
보내면 대개 1초 안팎에 답한다. 느린 요청을 끝까지 기다리는 대신, 늦어지면 하나를 더 보내 먼저 오는 쪽을 쓴다(꼬리 지연 대응의
표준 기법).

**어떻게.** `app/llm.py`의 `_hedged_stream`:
- 주 대상(NVIDIA) 스트림이 `HEDGE_AFTER_S`초 안에 첫 토큰을 못 내면 **같은 대상에 동일한 요청**을 하나 더 보낸다.
- 두 요청 중 **첫 토큰을 먼저 낸 쪽**의 토큰만 전달하고, 진 쪽은 전달을 시작하기 전에 취소한다 — 각 요청은 자기 태스크에서
  돌기 때문에 태스크를 `cancel()`한 뒤 끝날 때까지 `await`하며, 이때 `_stream_once`의 `async with`가 응답과 클라이언트를
  닫는다(연결 누수·"Task was destroyed" 경고 없음). 소비자가 중간에 끊겨도(12초 마감 타임아웃) `finally`에서 같은 정리를 한다.
- 한쪽이 첫 토큰 전에 실패하면 경주에서 빠지고 다른 쪽을 기다린다. 둘 다 실패하면 기존대로 폴백 대상(로컬)으로 넘어간다.
  이긴 쪽이 출력 도중 끊기면 지금처럼 그대로 오류가 올라간다(템플릿 폴백).
- 주 대상이 헤지 시간 전에 바로 실패하면(예: HTTP 500) 헤지하지 않고 곧장 폴백 대상으로 간다. 폴백 대상(로컬)은 헤지하지 않는다.

**파라미터.** `HEDGE_AFTER_S` 기본 3.0초(환경 변수, `0`이면 끔 → 요청 1개). 3초는 평소 첫 토큰 p95(1.37초)의 두 배 이상이라
정상 요청에는 거의 발사되지 않고, 헤지가 12초 마감 안에 답할 시간(~9초)을 남긴다.

**비용.** 느릴 때만, 카드 하나당 요청이 **최대 1개** 더 나간다(헤지의 헤지는 없음). 진 요청은 즉시 취소되므로 추가 토큰 비용은
대개 첫 토큰 이전 구간뿐이다. 무료 등급 레이트 리밋에 여유가 있는 동안은 문제되지 않는다.

**관측.** 텔레메트리 줄에 `hedged`(헤지 발사 수)와 `hedge_won`(헤지 쪽이 이긴 수) 카운터가 요청 단위로 쌓이고,
`scripts/ops/prod_stats.py`가 둘을 합산해 보여준다. `hedged` 대비 `hedge_won`이 낮으면 3초가 너무 이른 것이므로 늘리고,
폴백이 여전히 남으면 줄이는 식으로 조정한다.

## 폴백 원인 분해와 조기 실패 재시도 (2026-09-28)

**왜.** 운영에서 여전히 카드 10장 중 1~2장이 템플릿으로 폴백된다는 보고가 있었다. 헤지(첫 토큰 3초 무응답 → 같은 요청 하나 더)는
"느린 요청"만 겨냥한다 — 원인이 정말 꼬리 지연인지부터 쟀다.

**운영 48시간 (Render 로그, `scripts/ops/prod_stats.py --hours 48`, [prod_stats_2026-09-28.json](../../data/eval/prod_stats_2026-09-28.json)).**
요청 54건(analyze 52, recommend 2), 카드 56장 중 **폴백 5장(0.089)**. 이 시점의 텔레메트리에는 원인 필드가 없어 줄마다
추정했다: 폴백 5장 모두 **첫 토큰 기록이 없고, `/analyze` 요청 전체가 1.1~1.7초에 끝났다**(임베딩·파싱 포함) — 12초 마감
타임아웃(첫 토큰 전/도중)도, 스트림 도중 끊김도, `max_tokens` 잘림도 아니라 **설명 스트림이 토큰 하나 없이 곧바로 실패**한
것이다. 헤지는 48시간 동안 1번 발사됐고 이기지 못했다(주 요청이 8.1초에 먼저 답함). 첫 토큰 p50 705ms / p95 1,184.5ms.

**로컬 재현.** 주 대상(NVIDIA)만 직접 부르면 빠른 실패가 두 가지 모양으로 나온다: 연속 60회 중 7회가 **HTTP 429 Too Many
Requests**(~0.45초), 스트림 30회 중 1회가 **본문 없는 200 스트림**(0.51초, 오류도 내용도 없음). 운영의 `/analyze`는
임베딩·파싱·설명이 모두 같은 NVIDIA 키를 쓰고, 평가 스크립트가 10건씩 연달아 부르는 구간에서 폴백이 몰려 있었다
(00:24, 13:38). 기존 코드에서 이런 실패는 헤지 타이머(3초)가 돌기 전에 끝나므로 헤지가 끼어들 틈이 없고, 곧장 폴백 대상
(로컬 Ollama)으로 넘어가는데 **운영(Render)에는 Ollama가 없어** 그대로 템플릿이 된다. 로컬 `bench` 3회(순차/병렬
4.32/5.53 · 6.23/4.58 · 5.14/2.6초, 첫 토큰 0.65~1.09초)는 이 문제를 못 잡는다 — 로컬 폴백이 살아 있고 호출 수가 적어서다.

**결정: 조기 실패 재시도.** `app/llm.py` `_hedged_stream`에서 **첫 요청이 출력 없이 끝나면**(HTTP 오류 또는 빈 200 스트림)
헤지를 기다리지 않고 `EARLY_RETRY_BACKOFF_S`(기본 1.0초) 뒤 같은 요청을 한 번 더 보낸다. 헤지와 재시도는 **추가 요청 1개**
예산을 공유한다(재시도가 나가면 헤지는 없고, 헤지가 나간 뒤 주 요청이 실패하면 재시도도 없다) — 카드당 요청이 최대 2개인
원래 비용 한도 그대로다. `EARLY_RETRY=0`이면 끈다. 더 작은 대안들은 데이터가 지지하지 않았다: `HEDGE_AFTER_S`를 줄여도
0.5초 만에 끝나는 실패에는 닿지 않고, 마감(12초)이나 `max_tokens`(220)는 폴백 원인과 무관하며(타임아웃·잘림 0건), 설명
모델 교체는 실패가 모델 지연이 아니라 요청 거절이라 이유가 없다.

**측정 (운영과 같은 조건: 폴백 대상 제거, 임베딩+설명 연속 호출, 요청마다 재시도 끔/켬 교대, [phase2_fallback_retry.json](../../data/eval/phase2_fallback_retry.json)).**

|---|---|---|
| 1회차 (60/60) | 폴백 4 (6.7%) | **0** (재시도 3회, 3회 모두 성공) |
| 2회차 (80/80) | 폴백 6 (7.5%) | **0** (재시도 4회, 4회 모두 성공) |
| 합계 | **10/140 (7.1%)** | **0/140** |

재시도로 살린 카드의 첫 토큰은 2.2~3.8초(1초 대기 + 재요청)로, 12초 마감 안에 충분히 들어온다. 첫 토큰 p50은 켬/끔 모두
0.65~0.72초로 같다(재시도는 실패한 요청에만 나간다).

**관측 보강.** 이제 텔레메트리 줄에 폴백 원인이 카운터로 남는다(`app/graphs/common.py` `fallback_reason`):
`fb_timeout_first_token` · `fb_timeout_midstream` · `fb_error_before_token` · `fb_error_midstream` · `fb_truncated_empty` ·
`fb_empty`, 그리고 재시도 횟수 `retried`. `prod_stats.py`는 이 카운터를 합산하고(`폴백 원인` 행), 원인 필드가 없는 예전
줄은 `ms_first_token`·`ms_total`로 추정해(`inferred_before_token_fast_error` 등) 같은 표에 넣는다. Render 로그 API의
429·503·읽기 타임아웃도 같은 페이지를 백오프 후 다시 요청하게 했다(48시간 조회가 매번 중간에 죽었다).

**다음에 볼 것.** 배포 후 `prod_stats.py --hours 48`에서 `fb_error_before_token`이 남아 있으면 — 재시도까지 둘 다 429라는
뜻이므로 — 요청 간 간격(레이트 리밋 창)을 늘리는 쪽(예: `EARLY_RETRY_BACKOFF_S` 2초)을 검토한다.

## 조기 실패 재시도 2회와 설명 캐시 (2026-09-29)

운영 24시간(두 서비스, 요청 224건) 폴백 45건 중 38건이 첫 토큰 전 실패(`error_before_token` — NVIDIA 429·빈 응답)였다. 조기 실패 재시도 1회(1초 뒤)로는 429가 이어지는 동안 모자랐다(재시도 106회). 두 가지를 바꿨다.

- **재시도 최대 2회**: 첫 토큰 전에 끝난 요청이 또 실패하면 한 번 더, 멈춤은 1초 → 2초(`EARLY_RETRY_MAX=2`, 12초 마감 안). 헤지가 이미 나간 뒤에는 재시도하지 않는다.
- **설명 캐시**: 모델 입력(시스템 문구 + 페이로드)이 같으면 검사를 통과한 설명을 다시 쓴다(`app/graphs/common.py`, 프로세스당 1,024개, 오래된 것부터 버림). 온보딩 프리셋은 같은 프로필을 만들어 시연·심사에서 같은 카드가 반복되고, 같은 브랜드를 다시 누르는 경우도 같다. 폴백은 캐시에 넣지 않는다. 텔레메트리 `cached`로 센다.

결과(배포 뒤 운영, 같은 64카드 확인을 두 번 — 페르소나 3 × 브랜드 5 + 원두 분석, 두 판): 카드 128장 폴백 **0**(배포 전 24시간 폴백 비율 0.060 · 0.141), 조기 실패 재시도 19회가 모두 살아났고 두 번째 확인의 설명 45개는 캐시에서 바로 나갔다(Render 로그 1시간 집계).
