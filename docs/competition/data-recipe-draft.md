> **카페인·우유 조건을 반드시 지키는 커피 추천 — 공개 원두 품질 데이터와 국내 로스터리 사실정보 기반 RAG 레시피**

(더 짧게: "디카페인·저카페인 사용자를 위한 조건 보장형 커피 추천 AI 레시피")

### A-2. 신청 개요 (300자 이상 · Why/What/How/Outcome)
건강 때문에 카페인을 줄여야 하지만 커피 맛은 포기하고 싶지 않은 사람이 많다. 카페 메뉴판에는 카페인 함량이나 디카페인 변경 가능 여부, 산미·바디 같은 맛 정보가 흩어져 있어, 조건이 있는 사람은 매번 검색하거나 익숙한 메뉴만 고른다(Why). 이 과제는 프랜차이즈 3사의 공식 메뉴 304종(카페인 mg, 디카페인 여부)과 **오픈 라이선스 원두 품질 데이터(CQI 커핑 점수, RoasterDB)**, 그리고 robots.txt를 지켜 모은 **국내 로스터리 12곳의 원두 사실정보 209건**을 하나의 구조로 합쳤다(What). 카페인·우유 조건은 SQL 필터로 **반드시** 걸러내고, 남은 후보만 취향 점수로 정렬하며, 정보가 없는 원두는 임베딩 기반 이웃 10개로 산미·바디를 예측하고 신뢰도를 함께 보여준다. 설명 문장은 LLM이 쓰되 12초 안에 끝나지 않으면 템플릿 문장으로 바꾼다(How). 그 결과 조건 위반이 한 건도 없었고, 디카페인 원두 후보가 6개에서 23개(국내 로스터리 17개 추가)로 늘어난 것을 확인했으며, 마신 기록이 쌓일수록 취향 프로필 오차가 줄어드는 것을 확인했다(정확한 수치는 1장 수치 표 참고, Outcome).

### A-3. 추진배경 및 문제 정의 (300자 이상 · ①원인 ②데이터로 확인 가능한 부분 ③해결 방법)
① **원인**: 임산부, 수면장애가 있는 사람, 카페인에 민감한 사람처럼 카페인을 제한해야 하는 사람은 "무엇을 마시면 안 되는가"는 알지만 "그 안에서 무엇이 내 입맛에 맞는가"는 알기 어렵다. 식약처가 권고하는 하루 최대 카페인 섭취량은 성인 400mg, 임산부 300mg, 어린이·청소년 체중 1kg당 2.5mg이다(한국소비자원 2022 즉석커피 보도자료가 인용한 식약처 2020 자료). 그런데 같은 아메리카노라도 브랜드마다 샷 수가 달라 카페인 차이가 크고, 디카페인으로 바꿀 수 있는지, 추가 요금이 얼마인지, 우유가 들어가는지(마키아또·플랫 화이트 등 이름만으로는 모르는 메뉴)는 브랜드마다 표기 방식이 다르다.
② **데이터로 확인되는 것**: 수집한 3개 브랜드 메뉴 304종 중 디카페인 메뉴는 74종이고, 카페인 mg가 적힌 메뉴는 299종이다. 반면 디카페인 원두는 오픈 라이선스 원두 1,655개 중 6개뿐이고, 그 가운데 국내에서 살 수 있는 것은 블루보틀 코리아의 1개뿐이었고, 그마저 산미 정보가 없다. 조건을 지키면서 고를 수 있는 선택지 자체가 데이터상 매우 적다.
③ **해결 방법**: 조건(카페인 규칙 decaf_only / low(≤100mg) / any, 우유 가능 여부)은 추천 점수에 섞지 않고 **DB 필터로 먼저 걸러** 위반 가능성을 구조적으로 없앤다. 그다음 산미·바디·단맛·향미 취향 점수로 정렬하고, 데이터가 비어 있는 원두는 비슷한 원두로 값을 예측하되 신뢰도를 함께 보여준다. 국내 로스터리 원두를 더해 "국내에서 실제로 살 수 있는 디카페인" 후보를 늘린다.

### A-4. 데이터 분석 기획 (300자 이상)
- **이 방식을 쓰는 이유**: 맛 취향은 개인차가 커서 규칙만으로는 맞추기 어렵고, 카페인 같은 조건은 틀리면 안 된다. 그래서 "조건은 규칙(필터), 취향은 데이터(유사도·점수)"로 역할을 나눴다. 예전 와인 추천 버전에서 필터를 프롬프트 문장으로만 넘겼더니 실제로는 걸러지지 않았던 경험이 있어, 이번에는 조건을 SQL WHERE로 강제했다.
- **분석 주제와 목표(측정 가능)**: ① 조건 위반율 0%(페르소나 4개 × 브랜드 10개, 추천 상위 3개). ② 정보가 없는 원두의 산미·바디 예측이 사람 평가(CQI 커핑)와 ±1 안에 드는 비율과, 신뢰도가 높을수록 더 정확한지. ③ 국내 로스터리 데이터를 더했을 때 디카페인 후보·향미 태그 커버리지가 얼마나 늘어나는지. ④ 음용 기록이 쌓일수록 취향 프로필 오차가 줄어드는지.
- **데이터 선정 이유와 확보 방법**: 저작권 문제가 없는 데이터만 쓰기 위해 **Kaggle의 coffeereview.com 리뷰 스크랩(원 저작권은 Coffee Review)은 이 제출본에서 뺐다.** CQI는 MIT 라이선스 저장소에서, RoasterDB는 CC BY-NC 4.0 샘플에서 받았고, 브랜드 메뉴와 국내 로스터리는 robots.txt가 허용한 범위에서 호스트마다 1초씩 간격을 두고 한 번만 수집했으며 설명 문구(산문)는 저장하지 않았다.
- **도구·기법**: Python, PostgreSQL + pgvector(HNSW), NVIDIA nemotron-3-embed-1b 임베딩(앞 1024차원 사용), 로컬 LLM(qwen3.5 9B)으로 빈 칸 구조화, LangGraph로 추천·원두 분석·기록 흐름을 구성, FastAPI + Next.js 웹앱.

### A-5. 데이터 개요 및 데이터 활용(분석) 방안 (300자 이상)
**데이터**: 원두 1,864개(오픈+로스터리판: CQI 1,546 · RoasterDB 100 · 블루보틀 코리아 9 · 국내 로스터리 209), 프랜차이즈 메뉴 304종, 브랜드 10곳의 디카페인 정보, SCA 향미 분류 121개 한국어 매핑. 출처와 라이선스는 아래 3장 표에 정리했다.
**전처리**: ① 소스별 원본 스냅샷을 날짜별로 저장 ② 공통 스키마로 정규화(산지·가공·로스팅 표기 통일, 이름·설명에서 디카페인 판별) ③ 한국어 향미 노트 단어("초콜릿, 건무화과, 호두")를 SCA 휠 한국어 이름·별칭으로 규칙 매핑 ④ 규칙으로 못 채운 산미·바디·단맛만 로컬 LLM이 JSON 스키마로 채우고, 근거가 없으면 null로 둠 ⑤ 이름·산지·가공·노트를 nemotron-3-embed-1b로 임베딩해 pgvector에 한 트랜잭션으로 적재 ⑥ 우유 포함 여부는 메뉴 이름 302종에 사람이 직접 라벨을 붙여 평가 기준으로 따로 둠.
**분석**: 하드 조건 필터 → 취향 적합도(속성 0.6 + 향미 0.4) → MMR로 다양성을 살린 상위 3개 → LLM 설명(실패 시 템플릿). 처음 보는 원두는 코사인 유사도 상위 10개 이웃의 가중 평균으로 산미·바디를 예측하고, 이웃 간 일치도로 신뢰도(high/medium/low)를 매긴다. 검증은 CQI 원두 200개를 고정한 leave-one-out으로 하고, 데이터 구성(전체/오픈/오픈+로스터리)만 바꿔 같은 지표를 비교했다.

### A-6. 예상성과(실제성과) 및 기대효과 (300자 이상)
- **실제 성과(측정값, 1장 수치 표 · `data/eval/open/*.json`)**: 조건 위반 0건(이전 로직에서는 위반이 있었다 — 마키아또·콘 파나·플랫 화이트를 우유 불가 손님에게 추천했었다). 국내 로스터리를 더하자 디카페인 원두가 6→13개(국내 로스터리 7개), 향미 태그가 있는 원두가 109→148개로 늘었다. 모의 사용자 200명이 10번 기록한 뒤 프로필 오차가 줄었다(1장 표). 설명 3개를 병렬로 만들어 지연시간을 크게 줄였고(1장 표), 2문장 규칙을 통과한 설명이 24건 중 21건(87.5%), 두 판정자 모두 무모순 72.7%·무환각 59.1%였다(`phase2_explain_quality.json`).
- **사회적 가치**: 카페인을 줄여야 하는 사람(임산부, 수면장애, 심혈관 질환자, 청소년)이 "안전한 선택지 안에서 맛있는 선택"을 할 수 있다. 조건은 필터로 강제하므로, LLM이 틀린 설명을 하더라도 조건을 어긴 음료는 추천 목록에 아예 오르지 않는다.
- **산업적 효과**: 소규모 로스터리는 원두 정보가 적어 추천에 잘 걸리지 않는데, 이웃 예측과 신뢰도 표시로 정보가 적은 원두도 후보에 올릴 수 있다. 브랜드 입장에서는 디카페인 옵션과 추가 요금 정보가 구조화되면 디카페인 수요를 매출로 연결할 수 있다.
- **확산 가능성**: "조건은 필터, 취향은 점수, 모르는 값은 이웃으로 예측하고 신뢰도 공개"라는 구조는 알레르기·당류 제한이 있는 음식 메뉴 추천, 와인·차 추천에 그대로 옮길 수 있다.
- **후속 계획**: ① 식약처 식품영양성분DB(카페인 필드)로 나머지 7개 브랜드의 카페인을 채우고 브랜드 공지값과 교차검증 ② 소상공인 상권정보로 "지금 근처에서 갈 수 있는 브랜드"만 추천 ③ 관세청 디카페인 원두 수입 통계로 수요 추세를 문제 정의 근거로 보강 ④ 원두 카드·메뉴판 사진에서 정보를 뽑는 Vision 단계.

### B-2. 2단계 레시피 개요
- **이 레시피로 얻을 수 있는 것**
  1. 카페인·우유 조건을 한 번도 어기지 않는 음료·원두 추천 목록(상위 3개)과 추천 이유
  2. 정보가 없는 원두의 산미·바디 예측값과 신뢰도(high/medium/low)
  3. 마신 기록(별점·한 줄 후기)이 쌓일수록 자동으로 바뀌는 취향 프로필
- **추천 대상**: 디카페인·저카페인 사용자를 위한 서비스를 만드는 커피 앱·카페 프랜차이즈, 원두 큐레이션을 하는 소규모 로스터리, 건강관리 앱
- **이 레시피가 필요한 이유**: 카페인을 줄여야 하는 사람은 메뉴판에서 "마셔도 되는 것"을 먼저 추려야 하는데, 카페인 mg·디카페인 변경 여부·우유 포함 여부가 브랜드마다 다르게 적혀 있다. 추천 시스템이 조건을 점수의 일부로만 다루면 점수가 높은 위반 메뉴가 올라올 수 있다. 이 레시피는 조건을 필터로 먼저 적용한 뒤에만 취향 점수를 계산하고, 그 결과를 조건 위반율로 따로 검증한다.
- **필요 데이터(필수)**: 메뉴명, 디카페인 여부, 디카페인 변경 가능 여부, 카페인(mg), 우유 포함 여부 라벨 / 원두명, 산지, 가공방식, 로스팅, 디카페인 여부
- **선택적 데이터**: 산미·바디·단맛 점수(1~5), 향미 노트 단어, 가격, 브랜드별 디카페인 추가요금
- **최소 데이터 요건**: 메뉴 100종 이상(디카페인 메뉴 포함), 산미·바디가 사람 평가로 매겨진 원두 500개 이상(이웃 예측의 근거 풀)
- **예측하려는 값**: 처음 보는 원두의 산미·바디(1~5 척도)와 사용자별 추천 적합도 점수
- **데이터 형식**: CSV/JSONL(표), PostgreSQL + pgvector
- **얻는 결과**: 조건을 통과한 상위 3개 추천 카드 + 예측 속성·신뢰도 + 설명 문장
- **준비 사항**: PostgreSQL(pgvector 확장), 임베딩 모델(NVIDIA API nemotron-3-embed-1b, 로컬 대안 bge-m3), 선택적으로 LLM API(없으면 템플릿 설명으로 동작)
- **주의 문구**: 원두의 산미·바디가 비어 있거나 사람 평가가 아닌 추정값이면 예측 신뢰도가 낮아진다. 같은 텍스트를 가진 중복 원두가 많으면 이웃 선택이 흔들린다(±1~3%p). 카페인 mg가 없는 메뉴는 "저카페인" 조건에서 자동으로 빠진다.

### B-4. 4단계 활용 가능 데이터 셋

- **데이터 구분 / 출처 / 테이블명**: 아래 3장 표에서 **"포털 업로드 가능" 열이 ○인 것만** 올린다.

  - 테이블 3 `eval_results` — 평가 결과 집계(위반율, LOO, 커버리지)
- **컬럼정의 파일(CSV)**: 완료 — `data/competition/01_컬럼정의.csv`(`scripts/competition/export_csv.py`로 생성, coffees/menu_items/brands 순, "변수번호, 타깃 여부, 타입, 컬럼명, 비고" 형식).
- **데이터 템플릿 예시·데이터셋 파일(CSV)**: 완료 — `data/competition/02_데이터_템플릿.csv`(테이블별 3행), `03_데이터셋_coffees.csv`(source ∈ {cqi, roasters_kr, shopify}), `04_데이터셋_menu_items.csv`, `05_데이터셋_brands.csv`, `06_데이터셋_milk_labels.csv`(업로드 세트 = 01~06, UTF-8 BOM). - **데이터 변수 가이드라인**: 독립변수 — 원두 텍스트 임베딩(이름·산지·가공·로스팅·노트), 산지, 가공방식, 사용자 취향(산미·바디·단맛·향미 가중치). 종속변수 — 원두의 산미·바디(LOO 정답은 CQI 커핑 점수를 5분위로 바꾼 값), 추천 적합도.

### B-5. 5단계 데이터 분석 프로세스 (최대 6단계, 라벨 8자 이내 권장)
| STEP | 라벨 | 설명 |
|---|---|---|
| 1 | 수집·정규화 | robots.txt를 지키고 호스트마다 1초 간격으로 한 번만 수집. 소스별 원본을 날짜별 스냅샷으로 저장. 공통 스키마로 합치고 산지·가공·로스팅 표기를 통일하며 이름·설명에서 디카페인 여부를 판별한다. coffeereview(Kaggle)는 제외한다. |
| 2 | 품질점검 | 필드별 결측률 리포트를 만들고, 소스 간 중복(같은 URL의 블루보틀 8건)을 제거하고, 메뉴 우유 포함 여부 302종을 사람이 라벨링해 독립 평가 기준으로 둔다. |
| 3 | 규칙+LLM | 향미 노트 단어를 SCA 한국어 사전으로 규칙 매핑. 규칙으로 못 채운 산미·바디·단맛만 로컬 LLM이 JSON 스키마로 채우고, 근거가 없으면 null로 둔다. 결과를 캐시해 중간에 끊겨도 이어서 실행된다. |
| 4 | 임베딩적재 | nemotron-3-embed-1b(앞 1024차원)로 임베딩해 pgvector(HNSW)에 한 트랜잭션으로 적재. 디카페인처럼 소수 조건으로 필터한 검색은 `hnsw.iterative_scan`으로 결과 k개를 채운다. |
| 5 | 필터·추천 | 카페인 규칙(decaf_only / low ≤100mg / any)과 우유 조건을 SQL로 먼저 거른다. 취향 점수(속성 0.6 + 향미 0.4) → MMR 상위 3개. 모르는 원두는 이웃 10개 가중 평균 + 신뢰도로 예측. 설명은 LLM 3개 병렬 스트리밍, 12초 안에 끝나지 않으면 템플릿 문장. |
| 6 | 평가 | 조건 위반율(페르소나 4 × 브랜드 10, 우유는 수기 라벨 기준), CQI 200개 고정 LOO, 데이터 구성 3가지 비교, 모의 사용자 수렴, 설명 지연시간. |

### B-6. 6단계 분석 결과 예시 (이미지 최대 5장, 이미지와 해석을 한 쌍으로)

1. **조건 위반율** ([`images/01_violations.png`](images/01_violations.png))

   ![조건 위반 히트맵](images/01_violations.png)

   페르소나 4개 × 브랜드 10개의 추천 상위 3개를 검사해 102건 중 위반 0건(0.0%)이었다(`phase2_violations.json`). 히트맵의 모든 칸이 0이라는 것은 특정 페르소나·브랜드 조합에 위반이 몰려 있지 않다는 뜻이다. 판정 기준(우유 수기 라벨, 원본 메뉴의 디카페인 필드)은 추천에 쓰는 코드와 독립적으로 만들어, 추천 로직의 버그를 놓치지 않게 했다. 이전 버전에서는 실제로 위반이 있었다(마키아또·콘 파나·플랫 화이트를 우유 불가 손님에게 추천) — 조건을 점수가 아닌 SQL 필터로 강제한 지금 버전에서는 재현되지 않는다.

2. **데이터 구성 3가지 비교** ([`images/02_loo_compare.png`](images/02_loo_compare.png))

   결측(`None`)이 됐다(CQI의 "Body"는 애초에 무게감이 아니라 큐핑 품질 점수였고, CQI엔 재판정할 리뷰
   원문도 없다). 이 비교의 LOO 대상 선정 게이트가 원래 "산미 AND 바디 둘 다 not null"이었던 탓에 한때
   대상 자체가 0개로 무너졌었는데, 게이트를 **"산미만 not null"**로 고쳐(`app/repo.py::
   random_coffee_ids_for_loo`) 대상 200개(CQI, 시드 42)를 재라벨 전과 동일하게 복원했다. **산미
   비교는 완전히 정상 작동**하고(세 구성 모두 0.495로 재라벨 전과 같다), 이 CQI 고정 대상으로는
   **바디를 구조적으로 못 잰다** — CQI 200개 "전원"의 바디가 결측이라, 대상을 몇 개를 뽑든 그 안에
   바디 정답이 하나도 없다(`n=0`, 버그 아님).

   그래서 바디는 **별도의 고정 대상 200개**(시드 42, coffeereview_kaggle 중 무게감 라벨이 있는

   coffeereview_kaggle 자체를 이웃 풀에서 빼므로(`VARIANTS`) 이 라벨이 그 두 판에 새어 들어갈 일이

### B-7. 7단계 예상성과 및 활용방안
- **성과지표(최대 3개, 보조설명은 10자 이내 권장)**
  1. 조건 위반율 — 보조설명 "0건, 0%(1장 표)"
  2. 디카페인 원두 후보 — 보조설명 "6→13개(국내 7)"
  3. 산미 예측 ±1 비율 — 보조설명 "high 신뢰도 0.71"
- **결과 해석**: 조건을 필터로 강제하는 구조 덕분에 위반율이 0%이고, 이는 원두 데이터 구성과 관계없이 유지된다(위반율은 프랜차이즈 메뉴에 대한 필터 정확도라 원두 지식베이스를 바꿔도 같은 지표로 측정된다). 오픈 데이터만 쓰면 산미 예측은 절반 정도만 ±1 안에 들어 전체 데이터판(모든 소스 대상 LOO 0.735)보다 낮다. 그래서 예측값만 보여주지 않고 신뢰도를 함께 보여준다. 국내 로스터리 사실정보는 예측력보다 "살 수 있는 선택지"를 늘리는 데 기여한다.
- **기대효과**: 카페인 제한이 있는 사용자가 매장에서 30초 안에 조건을 지키는 음료를 고를 수 있다. 소규모 로스터리 원두가 정보가 적어도 추천 후보에 오른다. 브랜드는 디카페인 옵션 정보를 구조화해 수요를 파악할 수 있다.
- **활용방안 도입문**: "조건은 필터로, 취향은 점수로, 모르는 값은 이웃으로 예측하고 신뢰도를 공개한다."
- **분석결과 활용방안(상세)**
  - 단기: 공개 웹앱으로 게스트 사용(로그인 없음) → <https://coffee-sommelier-open.vercel.app>(제출본, coffeereview 미포함), 코드와 재현 방법 → <https://github.com/gayeoniee/coffee-sommelier>. 전체 원두 데이터가 궁금하면 참고용 전체 포트폴리오판 <https://coffee-sommelier-psi.vercel.app>(제출용 아님)도 함께 볼 수 있다. 식약처 식품영양성분DB의 카페인 필드로 메뉴를 수집하지 못한 7개 브랜드(투썸플레이스·컴포즈·이디야·할리스·폴바셋·블루보틀·커피빈)의 카페인을 채운다.
  - 장기: 소상공인 상권정보(커피전문점 업종)와 결합해 위치 기반 추천, 관세청 디카페인 생두·원두 수입 통계(HS 0901.12 / 0901.22)로 수요 추세 대시보드, 알레르기·당류 조건이 있는 음식 메뉴 추천으로 확장.

### 공개 게이지 라벨과 해석 가능한 특징 모델

오픈 데이터의 산미 라벨(CQI)은 커핑 **품질** 점수라 "얼마나 신가"를 말해 주지 않는다. 그래서 국내 로스터리가 상품
페이지에 직접 공개한 **맛 게이지**(산미·바디·단맛 점/막대/숫자)를 사람 라벨로 모았다 — 커피 리브레 18건(점 5개)·
1킬로커피 37건(SENSORY CHART 막대)·G로스팅 17건(숫자 0~5)·내일의커피 10건(점 5개), 합계 82건(산미 82·바디 64·단맛 72).
HTML/텍스트로 보이는 게이지만 읽고(이미지 게이지 제외) 사이트별 척도를 기록한 뒤 1~5로 정규화했으며, 모든 라벨의
출처(`gauge`·`korean_cue`·`llm_review`·`cqi_quality`)를 `coffees.attr_label_source`에 남겼다.

이 라벨로 **산지 권역·고도 구간·가공·로스팅·품종·디카페인 공정·노트 단어의 SCA 범주 개수**를 특징으로 한 릿지 회귀를
학습했다. 로스터리 단위 교차검증(한 로스터리는 학습과 평가 중 한쪽에만)에서 ±1 이내 비율이 산미 **0.658**(오픈 이웃 평균
0.500, n=82), 단맛 **0.569**(0.514, n=72)로 기준(+0.05)을 넘어 제출본에 탑재했고, 바디는 0.797 vs 0.750(n=64)으로 미달이라
이웃 평균을 유지한다. 예측마다 기여가 큰 특징을 "과일 노트·고지대(1,900m)·약배전 → 산미↑"처럼 근거로 보여 준다.
CQI 품질 점수를 보조 라벨로 섞으면 오히려 나빠져(산미 MAE 0.863→0.913) 쓰지 않았다. 한계: 라벨이 로스터리 4곳뿐이라
로스터리마다 다른 척도 관행이 오차의 큰 몫이다(`data/eval/open/phase3_feature_model.json`, ADR 0011).

## 5. 한계와 개선 (정직하게)

- **오픈 데이터만 쓰면 예측이 약하고, CQI 고정 LOO만으로는 바디를 잴 수 없다.** 바디를 무게감으로 재라벨링하면서([ADR 0010](../adr/0010-body-heaviness.md)) CQI의 바디가 전부 결측이 됐다 — CQI 200개 고정 LOO(위 B-6 2번)는 산미(0.495)는 재라벨 전과 동일하게 재지만 바디는 CQI 200개 전원이 결측이라 이 대상으로는 정확도 자체가 없다(n=0, 대상 게이트를 산미만 요구하도록 고쳐 대상 자체는 복원했다). 그래서 바디는 별도의 coffeereview 고정 대상 200개(채점 전용, 앱·학습에는 미사용)로 따로 재고, 세 구성 모두 ±1 0.64 안팎(전체 0.64/n=200, 오픈 0.649/n=151, 오픈+로스터리 0.6391/n=169, 위 B-6 2번)이다. 제출본 DB(`coffee_open`) 전체를 대상으로 한 별도 LOO는 대상이 200개 그대로 나오지만(`data/eval/open/phase2_loo.json`), 바디 정답을 가진 원두가 6개뿐이라 n=6으로 작다. 모든 소스를 대상으로 한 포트폴리오판 자체 LOO(산미 0.735, 바디 0.6405/n=153)는 대상 원두 자체가 다르다(CQI 대신 coffeereview 위주).
- **제출본 속성 모델: 이제 세 속성 모두 이웃 평균만 쓴다.** coffeereview·RoasterDB를 빼고 CQI(사람 커핑 점수) + 국내 로스터리 + shopify 원두만으로 산미·바디 회귀 모델을 따로 학습해 왔는데(`config/attr_model_open.json`), 바디 학습 표본이 CQI 결측으로 **1,379건 → 31건**으로 무너져 최소 기준(300건) 미달이라 바디 헤드를 뺐다. 산미는 라벨 수(1,373건) 자체는 게이트를 통과하고, 대상 게이트 수정 후 held-out도 진짜 200개로 복원돼(재라벨 전과 동일 대상) 모델이 이웃 평균보다 MAE·±1 둘 다 나쁘다는 걸 신뢰할 수 있는 표본으로 재확인했다(1.14/0.45 vs 1.1004/0.48) — ADR 0009의 판단(MAE 1.14 vs 1.0981)과 사실상 같은 결론이라 정책을 유지해 산미도 탑재하지 않는다. `config/attr_model_open.json` 자체가 이제 없다 — **제출본은 산미·바디·단맛 모두 이웃 평균으로 예측한다.** 향미도 오픈판 전용(SCA 7대 카테고리 분류기)을 5-fold CV로 시험했지만 카테고리 F1 0.6459가 이웃 투표 0.6593을 넘지 못해 탑재하지 않았다 — 표본(145건)이 전체 카탈로그를 이웃으로 쓰는 투표보다 정보량이 적기 때문이다. 정직하게 기록한다: 라이선스가 깨끗한 데이터만으로는 학습 모델이 이웃 평균을 이기지 못했고, 이번 바디 재정의로 그 표본마저 더 줄었다. 자세한 수치는 [ADR 0009](../adr/0009-learned-attribute-model.md), [ADR 0010](../adr/0010-body-heaviness.md), `data/eval/phase2_attr_model_open.json`, `data/eval/open/phase2_loo.json`.
- **오픈판은 미지 원두의 향미를 거의 말하지 못한다.** 한국어 원두 문구 10개를 두 배포에 넣어 비교하면(`data/eval/phase2_analyze_compare.json`), 향미 태그를 제시한 원두가 전체판 10/10, 오픈판 3/10이고 속성 결측이 1/30 vs 8/30이다(CQI에는 단맛·향미 노트가 없음). 프랜차이즈 추천과 설명 품질은 두 판이 같다. 국내 로스터리 사실정보를 더 모으는 것이 오픈판의 가장 큰 개선 여지다.
- **동점 잡음**: CQI 원두 1,546개 중 744개가 임베딩이 완전히 같은 쌍둥이라, 재적재로 행 순서만 바뀌어도 LOO가 1~3%p 움직인다.
- **로스터리 데이터의 공백**: 국내 디카페인 7개 중 4개(1kg커피)는 노트가 없어 태그·산미가 비어 있고, 추천 점수 계산에서 근거 없음으로 빠진다. 노트가 없는 68건은 이름·산지·가공만 임베딩된다. 제출본 DB 전체를 대상으로 한 LOO는 200개 중 198개만 예측되었다(`data/eval/open/phase2_loo.json`, 바디 n=198) — 근거 없는 원두가 이웃 풀을 희석해 예측이 빠지는 경우가 있다는 신호다.
- **로스터리 원두의 산미·바디는 LLM 추정값**이라 LOO 대상에서 뺐다. 즉 국내 원두에 대한 예측 정확도는 아직 측정하지 못했다.
- **메뉴 수집은 3개 브랜드뿐**(나머지 7개는 브랜드 정보만). 카페인 mg가 있는 메뉴는 304종 중 299종(2026-09-26 DB 조회).
- **향미 태깅 품질 평가(정답셋 50건, 규칙 태그 Jaccard 0.40)는 coffeereview를 포함한 데이터에서 뽑은 것**이라 제출본 결과로 쓰면 안 된다 → 오픈 데이터로 다시 표본을 뽑아 평가해야 한다.
- **정답 라벨이 사람 라벨이 아니다.** 평가 라벨은 다른 LLM 두 개가 붙인 실버 라벨이다(judge 간 산미 ±1 일치 100%).
- **런타임 분리**: 평가 코드는 `exclude_sources`로 coffeereview를 뺄 수 있지만, **앱이 실제로 쓰는 DB에서는 아직 빠져 있지 않다.** 시연·배포 전에 coffeereview 없이 DB를 다시 만들어야 한다(체크리스트 참고).
- 우유 판정 수기 라벨은 한 사람이 붙였다(검수자 없음).
- **제출본은 학습형 태그 모델을 쓰지 않는다** — 학습 데이터가 coffeereview 파생(`config/tag_model.json`, [ADR 0008](../adr/0008-learned-tag-model.md)). `DATA_VARIANT=open`이면 자동으로 적재하지 않고 기존 이웃 투표만 쓴다.

## 6. 재현 방법

```bash
docker compose up -d db                       # Postgres 17 + pgvector
uv sync
ollama pull qwen3.5:9b   # 임베딩은 NVIDIA API(NVIDIA_API_KEY)
cp .env.example .env                          # NVIDIA_API_KEY는 선택(없으면 템플릿 설명)

# 제출본(coffeereview 제외) 수집 — Kaggle 키 불필요
uv run python -m pipeline run --only collect --source cqi --source roasterdb --source sca_wheel \
    --source starbucks --source mega --source paik --source shopify
uv run python -m pipeline roasters-kr         # 국내 로스터리 사실정보(robots.txt 준수)
uv run python -m pipeline run --only normalize --only enrich --only embed --only load
# 【확인 필요】 normalize가 data/raw에 남은 예전 Kaggle 스냅샷까지 읽지 않는지 확인하고, 필요하면 깨끗한 RAW_DIR에서 실행

uv run python -m app.eval violations          # 조건 위반율 → data/eval/phase2_violations.json
uv run python -m app.eval compare3            # 전체/오픈/오픈+로스터리 → data/eval/phase2_compare3.json
uv run python -m app.eval convergence bench
uv run pytest -q
COOKIE_SECURE=false uv run uvicorn app.api:get_app --factory --port 8000
```

LOO 대상은 `target_ids_sha1 = d652320c4072789d0291eebd9d8a1605e1a72d2b`(CQI 200개, seed 42)로 고정되어 있어 세 판에서 같은 원두를 평가했는지 해시로 확인할 수 있다.

## 7. 본선 발표 대비 (평가 항목별 한 줄)
- 문제해결력: "조건은 필터, 취향은 점수" — 수정 전 3/78 위반 사례로 필터가 왜 필요한지 보여준다.
- 성과이해도: LOO 0.5가 뜻하는 것과, 신뢰도로 그 한계를 사용자에게 알리는 방식.
- 의사결정 설명력: coffeereview를 뺀 이유(저작권), LangGraph를 쓴 곳과 안 쓴 곳(ADR 0002), 병렬 설명의 실측(13.13→2.03초).
- 전달력: 디카페인+산미 페르소나 한 명의 여정(온보딩 → 추천 → 기록 → 프로필 변화) 시연.
- 질의응답 예상: "LLM이 틀린 설명을 하면?" → 조건 판정은 LLM 밖에서 하고, 12초 안에 끝나지 않으면 템플릿으로 바꾼다. "공공데이터는?" → 4장.
