### A-1. 과제명 ("문제 + 활용 데이터 + 방법/결과")
> **카페인·우유 조건을 반드시 지키는 커피 추천 — 공개 원두 품질 데이터와 국내 로스터리 사실정보 기반 RAG 레시피**

(더 짧게: "디카페인·저카페인 사용자를 위한 조건 보장형 커피 추천 AI 레시피")

### A-2. 신청 개요 (300자 이상 · Why/What/How/Outcome)
건강 때문에 카페인을 줄여야 하지만 커피 맛은 포기하고 싶지 않은 사람이 많다. 카페 메뉴판에는 카페인 함량이나 디카페인 변경 가능 여부, 산미·바디 같은 맛 정보가 흩어져 있어, 조건이 있는 사람은 매번 검색하거나 익숙한 메뉴만 고른다(Why). 이 과제는 프랜차이즈 3사의 공식 메뉴 304종(카페인 mg, 디카페인 여부)과 **오픈 라이선스 원두 품질 데이터(CQI 커핑 점수, RoasterDB)**, 그리고 robots.txt를 지켜 모은 **국내 로스터리 5곳의 원두 사실정보 107건**을 하나의 구조로 합쳤다(What). 카페인·우유 조건은 SQL 필터로 **반드시** 걸러내고, 남은 후보만 취향 점수로 정렬하며, 정보가 없는 원두는 임베딩 기반 이웃 10개로 산미·바디를 예측하고 신뢰도를 함께 보여준다. 설명 문장은 LLM이 쓰되 12초 안에 끝나지 않으면 템플릿 문장으로 바꾼다(How). 그 결과 조건 위반 0/78건, 디카페인 원두 후보가 6개에서 13개(국내 로스터리 7개 추가)로 늘어난 것을 확인했고, 마신 기록 10회로 취향 프로필 오차가 0.7792→0.7117로 줄었다(Outcome).

### A-3. 추진배경 및 문제 정의 (300자 이상 · ①원인 ②데이터로 확인 가능한 부분 ③해결 방법)
① **원인**: 임산부, 수면장애가 있는 사람, 카페인에 민감한 사람처럼 카페인을 제한해야 하는 사람은 "무엇을 마시면 안 되는가"는 알지만 "그 안에서 무엇이 내 입맛에 맞는가"는 알기 어렵다. 식약처가 권고하는 하루 최대 카페인 섭취량은 성인 400mg, 임산부 300mg, 어린이·청소년 체중 1kg당 2.5mg이다(한국소비자원 2022 즉석커피 보도자료가 인용한 식약처 2020 자료). 그런데 같은 아메리카노라도 브랜드마다 샷 수가 달라 카페인 차이가 크고, 디카페인으로 바꿀 수 있는지, 추가 요금이 얼마인지, 우유가 들어가는지(마키아또·플랫 화이트 등 이름만으로는 모르는 메뉴)는 브랜드마다 표기 방식이 다르다.
② **데이터로 확인되는 것**: 수집한 3개 브랜드 메뉴 304종 중 디카페인 메뉴는 74종이고, 카페인 mg가 적힌 메뉴는 299종이다. 반면 디카페인 원두는 오픈 라이선스 원두 1,655개 중 6개뿐이고, 그 가운데 국내에서 살 수 있는 것은 블루보틀 코리아의 1개뿐이었고, 그마저 산미 정보가 없다. 조건을 지키면서 고를 수 있는 선택지 자체가 데이터상 매우 적다.
③ **해결 방법**: 조건(카페인 규칙 decaf_only / low(≤100mg) / any, 우유 가능 여부)은 추천 점수에 섞지 않고 **DB 필터로 먼저 걸러** 위반 가능성을 구조적으로 없앤다. 그다음 산미·바디·단맛·향미 취향 점수로 정렬하고, 데이터가 비어 있는 원두는 비슷한 원두로 값을 예측하되 신뢰도를 함께 보여준다. 국내 로스터리 원두를 더해 "국내에서 실제로 살 수 있는 디카페인" 후보를 늘린다.

### A-4. 데이터 분석 기획 (300자 이상)
- **이 방식을 쓰는 이유**: 맛 취향은 개인차가 커서 규칙만으로는 맞추기 어렵고, 카페인 같은 조건은 틀리면 안 된다. 그래서 "조건은 규칙(필터), 취향은 데이터(유사도·점수)"로 역할을 나눴다. 예전 와인 추천 버전에서 필터를 프롬프트 문장으로만 넘겼더니 실제로는 걸러지지 않았던 경험이 있어, 이번에는 조건을 SQL WHERE로 강제했다.
- **분석 주제와 목표(측정 가능)**: ① 조건 위반율 0%(페르소나 4개 × 브랜드 10개, 추천 상위 3개). ② 정보가 없는 원두의 산미·바디 예측이 사람 평가(CQI 커핑)와 ±1 안에 드는 비율과, 신뢰도가 높을수록 더 정확한지. ③ 국내 로스터리 데이터를 더했을 때 디카페인 후보·향미 태그 커버리지가 얼마나 늘어나는지. ④ 음용 기록이 쌓일수록 취향 프로필 오차가 줄어드는지.
- **데이터 선정 이유와 확보 방법**: 저작권 문제가 없는 데이터만 쓰기 위해 **Kaggle의 coffeereview.com 리뷰 스크랩(원 저작권은 Coffee Review)은 이 제출본에서 뺐다.** CQI는 MIT 라이선스 저장소에서, RoasterDB는 CC BY-NC 4.0 샘플에서 받았고, 브랜드 메뉴와 국내 로스터리는 robots.txt가 허용한 범위에서 호스트마다 1초씩 간격을 두고 한 번만 수집했으며 설명 문구(산문)는 저장하지 않았다.
- **도구·기법**: Python, PostgreSQL + pgvector(HNSW), bge-m3 임베딩(1024차원), 로컬 LLM(qwen3.5 9B)으로 빈 칸 구조화, LangGraph로 추천·원두 분석·기록 흐름을 구성, FastAPI + Next.js 웹앱.

### A-5. 데이터 개요 및 데이터 활용(분석) 방안 (300자 이상)
**데이터**: 원두 1,762개(오픈+로스터리판: CQI 1,546 · RoasterDB 100 · 블루보틀 코리아 9 · 국내 로스터리 107), 프랜차이즈 메뉴 304종, 브랜드 10곳의 디카페인 정보, SCA 향미 분류 121개 한국어 매핑. 출처와 라이선스는 아래 3장 표에 정리했다.
**전처리**: ① 소스별 원본 스냅샷을 날짜별로 저장 ② 공통 스키마로 정규화(산지·가공·로스팅 표기 통일, 이름·설명에서 디카페인 판별) ③ 한국어 향미 노트 단어("초콜릿, 건무화과, 호두")를 SCA 휠 한국어 이름·별칭으로 규칙 매핑 ④ 규칙으로 못 채운 산미·바디·단맛만 로컬 LLM이 JSON 스키마로 채우고, 근거가 없으면 null로 둠 ⑤ 이름·산지·가공·노트를 bge-m3로 임베딩해 pgvector에 한 트랜잭션으로 적재 ⑥ 우유 포함 여부는 메뉴 이름 302종에 사람이 직접 라벨을 붙여 평가 기준으로 따로 둠.
**분석**: 하드 조건 필터 → 취향 적합도(속성 0.6 + 향미 0.4) → MMR로 다양성을 살린 상위 3개 → LLM 설명(실패 시 템플릿). 처음 보는 원두는 코사인 유사도 상위 10개 이웃의 가중 평균으로 산미·바디를 예측하고, 이웃 간 일치도로 신뢰도(high/medium/low)를 매긴다. 검증은 CQI 원두 200개를 고정한 leave-one-out으로 하고, 데이터 구성(전체/오픈/오픈+로스터리)만 바꿔 같은 지표를 비교했다.

### A-6. 예상성과(실제성과) 및 기대효과 (300자 이상)
- **실제 성과(측정값)**: 조건 위반 **0/78건**(수정 전 로직으로는 3/78건 — 마키아또·콘 파나·플랫 화이트를 우유 불가 손님에게 추천했었다). 국내 로스터리를 더하자 디카페인 원두가 6→13개(국내 로스터리 7개), 향미 태그가 있는 원두가 109→148개로 늘었다. 모의 사용자 200명이 10번 기록한 뒤 프로필 오차가 0.7792→0.7117로 줄었다. 설명 3개를 병렬로 만들어 13.95초→11.59초로 줄였다.
- **사회적 가치**: 카페인을 줄여야 하는 사람(임산부, 수면장애, 심혈관 질환자, 청소년)이 "안전한 선택지 안에서 맛있는 선택"을 할 수 있다. 조건은 필터로 강제하므로, LLM이 틀린 설명을 하더라도 조건을 어긴 음료는 추천 목록에 아예 오르지 않는다.
- **산업적 효과**: 소규모 로스터리는 원두 정보가 적어 추천에 잘 걸리지 않는데, 이웃 예측과 신뢰도 표시로 정보가 적은 원두도 후보에 올릴 수 있다. 브랜드 입장에서는 디카페인 옵션과 추가 요금 정보가 구조화되면 디카페인 수요를 매출로 연결할 수 있다.
- **확산 가능성**: "조건은 필터, 취향은 점수, 모르는 값은 이웃으로 예측하고 신뢰도 공개"라는 구조는 알레르기·당류 제한이 있는 음식 메뉴 추천, 와인·차 추천에 그대로 옮길 수 있다.
- **후속 계획**: ① 식약처 식품영양성분DB(카페인 필드)로 나머지 7개 브랜드의 카페인을 채우고 브랜드 공지값과 교차검증 ② 소상공인 상권정보로 "지금 근처에서 갈 수 있는 브랜드"만 추천 ③ 관세청 디카페인 원두 수입 통계로 수요 추세를 문제 정의 근거로 보강 ④ 원두 카드·메뉴판 사진에서 정보를 뽑는 Vision 단계.

### B-2. 2단계 레시피 개요
- **이 레시피로 얻을 수 있는 것**
  1. 카페인·우유 조건을 한 번도 어기지 않는 음료·원두 추천 목록(상위 3개)과 추천 이유
  2. 정보가 없는 원두의 산미·바디 예측값과 신뢰도(high/medium/low)
  3. 마신 기록(별점·한 줄 후기)이 쌓일수록 자동으로 바뀌는 취향 프로필
- **추천 대상**: 디카페인·저카페인 사용자를 위한 서비스를 만드는 커피 앱·카페 프랜차이즈, 원두 큐레이션을 하는 소규모 로스터리, 건강관리 앱
- **이 레시피가 필요한 이유**: 카페인을 줄여야 하는 사람은 메뉴판에서 "마셔도 되는 것"을 먼저 추려야 하는데, 카페인 mg·디카페인 변경 여부·우유 포함 여부가 브랜드마다 다르게 적혀 있다. 추천 시스템이 조건을 점수의 일부로만 다루면 점수가 높은 위반 메뉴가 올라올 수 있다. 이 레시피는 조건을 필터로 먼저 적용한 뒤에만 취향 점수를 계산하고, 그 결과를 조건 위반율로 따로 검증한다.
- **필요 데이터(필수)**: 메뉴명, 디카페인 여부, 디카페인 변경 가능 여부, 카페인(mg), 우유 포함 여부 라벨 / 원두명, 산지, 가공방식, 로스팅, 디카페인 여부
- **선택적 데이터**: 산미·바디·단맛 점수(1~5), 향미 노트 단어, 가격, 브랜드별 디카페인 추가요금
- **최소 데이터 요건**: 메뉴 100종 이상(디카페인 메뉴 포함), 산미·바디가 사람 평가로 매겨진 원두 500개 이상(이웃 예측의 근거 풀)
- **예측하려는 값**: 처음 보는 원두의 산미·바디(1~5 척도)와 사용자별 추천 적합도 점수
- **데이터 형식**: CSV/JSONL(표), PostgreSQL + pgvector
- **얻는 결과**: 조건을 통과한 상위 3개 추천 카드 + 예측 속성·신뢰도 + 설명 문장
- **준비 사항**: PostgreSQL(pgvector 확장), 임베딩 모델(bge-m3, 로컬 Ollama), 선택적으로 LLM API(없으면 템플릿 설명으로 동작)
- **주의 문구**: 원두의 산미·바디가 비어 있거나 사람 평가가 아닌 추정값이면 예측 신뢰도가 낮아진다. 같은 텍스트를 가진 중복 원두가 많으면 이웃 선택이 흔들린다(±1~3%p). 카페인 mg가 없는 메뉴는 "저카페인" 조건에서 자동으로 빠진다.

### B-3. 3단계 분석모델

### B-4. 4단계 활용 가능 데이터 셋
- **AI 활용 배경 목적**: 정보가 부족한 원두(국내 로스터리 원두의 대부분)에도 맛 속성을 추정해 추천 후보로 올리고, 추천 이유를 사람이 읽을 수 있는 문장으로 설명하기 위해 임베딩 검색과 LLM을 쓴다. 조건 판정에는 AI를 쓰지 않는다.
- **데이터 구분 / 출처 / 테이블명**: 아래 3장 표에서 **"포털 업로드 가능" 열이 ○인 것만** 올린다.
  - 테이블 1 `coffees_open` — 원두(CQI + 국내 로스터리 사실정보에서 뽑은 필드만)
  - 테이블 2 `menu_items` — 프랜차이즈 메뉴(이름, 디카페인, 변경 가능, 카페인 mg)【권리 확인 후】
  - 테이블 3 `eval_results` — 평가 결과 집계(위반율, LOO, 커버리지)
- **컬럼정의 파일(CSV)**: 【작성 필요: `db/schema.sql`의 `coffees`, `menu_items` 정의로 "변수번호, 타깃 여부, 타입, 컬럼명, 비고" 형식의 CSV를 만든다】
- **데이터 템플릿 예시·데이터셋 파일(CSV)**: 【작성 필요: 위 테이블에서 추출. RoasterDB·SCA 휠·coffeereview 파생 행은 넣지 않는다 — 3장 참고】
- **데이터 설명**: 원두 1행 = 원두 1개. 산미·바디·단맛은 1~5 정수, 향미 태그는 SCA 휠 영문 키 배열, `source`는 수집처, `is_decaf`는 규칙으로 판별한 값.
- **데이터 변수 가이드라인**: 독립변수 — 원두 텍스트 임베딩(이름·산지·가공·로스팅·노트), 산지, 가공방식, 사용자 취향(산미·바디·단맛·향미 가중치). 종속변수 — 원두의 산미·바디(LOO 정답은 CQI 커핑 점수를 5분위로 바꾼 값), 추천 적합도.

### B-5. 5단계 데이터 분석 프로세스 (최대 6단계, 라벨 8자 이내 권장)
| STEP | 라벨 | 설명 |
|---|---|---|
| 1 | 수집·정규화 | robots.txt를 지키고 호스트마다 1초 간격으로 한 번만 수집. 소스별 원본을 날짜별 스냅샷으로 저장. 공통 스키마로 합치고 산지·가공·로스팅 표기를 통일하며 이름·설명에서 디카페인 여부를 판별한다. coffeereview(Kaggle)는 제외한다. |
| 2 | 품질점검 | 필드별 결측률 리포트를 만들고, 소스 간 중복(같은 URL의 블루보틀 8건)을 제거하고, 메뉴 우유 포함 여부 302종을 사람이 라벨링해 독립 평가 기준으로 둔다. |
| 3 | 규칙+LLM | 향미 노트 단어를 SCA 한국어 사전으로 규칙 매핑. 규칙으로 못 채운 산미·바디·단맛만 로컬 LLM이 JSON 스키마로 채우고, 근거가 없으면 null로 둔다. 결과를 캐시해 중간에 끊겨도 이어서 실행된다. |
| 4 | 임베딩적재 | bge-m3(1024차원)로 임베딩해 pgvector(HNSW)에 한 트랜잭션으로 적재. 디카페인처럼 소수 조건으로 필터한 검색은 `hnsw.iterative_scan`으로 결과 k개를 채운다. |
| 5 | 필터·추천 | 카페인 규칙(decaf_only / low ≤100mg / any)과 우유 조건을 SQL로 먼저 거른다. 취향 점수(속성 0.6 + 향미 0.4) → MMR 상위 3개. 모르는 원두는 이웃 10개 가중 평균 + 신뢰도로 예측. 설명은 LLM 3개 병렬 스트리밍, 12초 안에 끝나지 않으면 템플릿 문장. |
| 6 | 평가 | 조건 위반율(페르소나 4 × 브랜드 10, 우유는 수기 라벨 기준), CQI 200개 고정 LOO, 데이터 구성 3가지 비교, 모의 사용자 수렴, 설명 지연시간. |

### B-7. 7단계 예상성과 및 활용방안
- **성과지표(최대 3개, 보조설명은 10자 이내 권장)**

  2. 디카페인 원두 후보 — 보조설명 "6→13개(국내 7)"
  3. 산미 예측 ±1 비율 — 보조설명 "high 신뢰도 1.0"
- **결과 해석**: 조건을 필터로 강제하는 구조 덕분에 위반율이 0%이고, 이는 원두 데이터 구성과 관계없이 유지된다(위반율은 프랜차이즈 메뉴에 대한 필터 정확도라 원두 지식베이스를 바꿔도 같은 지표로 측정된다). 오픈 데이터만 쓰면 산미 예측은 절반 정도만 ±1 안에 들어 전체 데이터판(모든 소스 대상 LOO 0.75)보다 낮다. 그래서 예측값만 보여주지 않고 신뢰도를 함께 보여준다. 국내 로스터리 사실정보는 예측력보다 "살 수 있는 선택지"를 늘리는 데 기여한다.

- **활용방안 도입문**: "조건은 필터로, 취향은 점수로, 모르는 값은 이웃으로 예측하고 신뢰도를 공개한다."

## 5. 한계와 개선 (정직하게)

- **오픈 데이터만 쓰면 예측이 약하다.** CQI 200개 고정 LOO에서 산미 ±1 이내 0.495~0.4975, 바디 0.525~0.54다(5점 척도에서 절반 정도만 ±1 안에 듦). 모든 소스를 대상으로 한 포트폴리오판 LOO(산미 0.75, 바디 0.65)는 대상 원두가 달라 직접 비교하면 안 된다.
- **동점 잡음**: CQI 원두 1,546개 중 744개가 임베딩이 완전히 같은 쌍둥이라, 재적재로 행 순서만 바뀌어도 LOO가 1~3%p 움직인다.
- **로스터리 데이터의 공백**: 국내 디카페인 7개 중 4개(1kg커피)는 노트가 없어 태그·산미가 비어 있고, 추천 점수 계산에서 근거 없음으로 빠진다. 노트가 없는 68건은 이름·산지·가공만 임베딩된다. n=199는 이웃 10개 중 8개가 산미 값이 없는 로스터리 원두여서 예측이 빠진 1건이다 — 근거 없는 원두가 이웃 풀을 희석할 수 있다는 신호다.
- **로스터리 원두의 산미·바디는 LLM 추정값**이라 LOO 대상에서 뺐다. 즉 국내 원두에 대한 예측 정확도는 아직 측정하지 못했다.
- **메뉴 수집은 3개 브랜드뿐**(나머지 7개는 브랜드 정보만). 카페인 mg가 있는 메뉴는 304종 중 299종(2026-09-26 DB 조회).
- **향미 태깅 품질 평가(정답셋 50건, 규칙 태그 Jaccard 0.40)는 coffeereview를 포함한 데이터에서 뽑은 것**이라 제출본 결과로 쓰면 안 된다 → 오픈 데이터로 다시 표본을 뽑아 평가해야 한다.
- **정답 라벨이 사람 라벨이 아니다.** 평가 라벨은 다른 LLM 두 개가 붙인 실버 라벨이다(judge 간 산미 ±1 일치 100%).
- **런타임 분리**: 평가 코드는 `exclude_sources`로 coffeereview를 뺄 수 있지만, **앱이 실제로 쓰는 DB에서는 아직 빠져 있지 않다.** 시연·배포 전에 coffeereview 없이 DB를 다시 만들어야 한다(체크리스트 참고).
- 우유 판정 수기 라벨은 한 사람이 붙였다(검수자 없음).

```bash

    --source starbucks --source mega --source paik --source shopify

uv run python -m pipeline run --only normalize --only enrich --only embed --only load
# 【확인 필요】 normalize가 data/raw에 남은 예전 Kaggle 스냅샷까지 읽지 않는지 확인하고, 필요하면 깨끗한 RAW_DIR에서 실행

uv run python -m app.eval violations          # 조건 위반율 → data/eval/phase2_violations.json
uv run python -m app.eval compare3            # 전체/오픈/오픈+로스터리 → data/eval/phase2_compare3.json
uv run python -m app.eval convergence bench
uv run pytest -q
COOKIE_SECURE=false uv run uvicorn app.api:get_app --factory --port 8000
```

LOO 대상은 `target_ids_sha1 = d652320c4072789d0291eebd9d8a1605e1a72d2b`(CQI 200개, seed 42)로 고정되어 있어 세 판에서 같은 원두를 평가했는지 해시로 확인할 수 있다.

## 7. 본선 발표 대비 (평가 항목별 한 줄)
- 문제해결력: "조건은 필터, 취향은 점수" — 수정 전 3/78 위반 사례로 필터가 왜 필요한지 보여준다.
- 성과이해도: LOO 0.5가 뜻하는 것과, 신뢰도로 그 한계를 사용자에게 알리는 방식.
- 의사결정 설명력: coffeereview를 뺀 이유(저작권), LangGraph를 쓴 곳과 안 쓴 곳(ADR 0002), 병렬 설명의 실측(13.95→11.59초).
- 전달력: 디카페인+산미 페르소나 한 명의 여정(온보딩 → 추천 → 기록 → 프로필 변화) 시연.
- 질의응답 예상: "LLM이 틀린 설명을 하면?" → 조건 판정은 LLM 밖에서 하고, 12초 안에 끝나지 않으면 템플릿으로 바꾼다. "공공데이터는?" → 4장.
